ソフトウェア

ソフトウェアライフサイクルプロセス

ソフトウェアの企画・開発・運用・保守・廃棄に至る一連の工程を、共通の枠組み・用語で整理した規格

| 分類 | 位置づけ | |---|---| | 1. 合意プロセス | 発注者・受注者間の「契約」に関するプロセス | | 2. 組織のプロジェクトイネーブリングプロセス | 組織全体としてプロジェクトを支える基盤整備プロセス | | 3. プロジェクトプロセス | 個々のプロジェクトのマネジメントに関するプロセス | | 4. テクニカルプロセス | システムレベルでの技術的な開発活動 | | 5. ソフトウェア実装プロセス | テクニカルプロセスをソフトウェア開発に特化させたもの | | 6. ソフトウェア支援プロセス | ソフトウェア開発を横断的に支える活動 | | 7. ソフトウェア再利用プロセス | 資産の再利用に関するプロセス |
##### 1. 合意プロセス (Agreement Processes) | プロセス | 内容 | |---|---| | 取得プロセス | 発注者側が必要なシステム・ソフトウェアを調達する活動(要求仕様の提示、提案評価、契約締結等) | | 供給プロセス | 受注者側が製品・サービスを提供する活動(提案、契約履行、納品等) |
##### 2. 組織のプロジェクトイネーブリングプロセス (Organizational Project-Enabling Processes) | プロセス | 内容 | |---|---| | ライフサイクルモデル管理プロセス | 組織で使うライフサイクルモデル・標準・手順を定義・維持する | | インフラストラクチャ管理プロセス | 開発・運用に必要な設備・ツール等の基盤を整備する | | ポートフォリオ管理プロセス | 複数プロジェクトへの資源配分・優先順位付けを行う | | 人的資源管理プロセス | 要員のスキル確保・教育訓練を行う | | 品質管理プロセス | 組織としての品質方針・品質マネジメントシステムを維持する | | ナレッジ管理プロセス | 組織内の知識・技術資産を蓄積・活用する |
##### 3. プロジェクトプロセス (Project Processes) | プロセス | 内容 | |---|---| | プロジェクト計画プロセス | スコープ・スケジュール・体制等の計画を立てる | | プロジェクト評価・制御プロセス | 計画に対する進捗・実績を評価し是正する | | 意思決定管理プロセス | プロジェクト内の重要な意思決定を管理する | | リスク管理プロセス | リスクの識別・分析・対応を行う | | 構成管理プロセス | 成果物のバージョン・変更履歴を管理する | | 情報管理プロセス | プロジェクトの情報(文書等)を管理する | | 測定プロセス | プロジェクトやプロセスの状況を定量的に測定する | | 品質保証プロセス | 成果物・プロセスが要求品質を満たすことを保証する |
##### 4. テクニカルプロセス(Technical Processes) - システム全体を対象とした、企画から廃棄までの技術的な活動 | プロセス | 内容 | |---|---| | 事業又は任務分析プロセス | 事業・業務上の課題やニーズを分析する | | 利害関係者ニーズ・要求事項定義プロセス | 利害関係者の要求を明確化する | | システム/ソフトウェア要求定義プロセス | システムに求める要件を定義する | | アーキテクチャ定義プロセス | システムの構造・方式を設計する | | 設計定義プロセス | システムの詳細な設計を行う | | システム解析プロセス | 設計の妥当性等を解析する | | 実装プロセス | システムを実際に作り上げる | | 統合プロセス | 構成要素を結合しシステムとして成立させる | | 検証プロセス | 仕様どおりに作られているかを確認する(Doing the right things) | | 移行プロセス | 新システムへの切り替え・移行を行う | | 妥当性確認プロセス | 利用者の要求を満たしているかを確認する(Doing the right product) | | 運用プロセス | 本番環境でシステムを稼働させる | | 保守プロセス | 稼働中のシステムを修正・改善する | | 廃棄プロセス | システムの利用を終了し処分する |
##### 5. ソフトウェア実装プロセス(Software Implementation Processes) - テクニカルプロセスの「実装」以降を、ソフトウェアに特化して詳細化したもの | プロセス | 内容 | |---|---| | ソフトウェア実装プロセス(親) | ソフトウェア実装全体の統括 | | ソフトウェア要求分析プロセス | ソフトウェアへの要求を分析する | | ソフトウェア方式設計プロセス | ソフトウェアの構造(アーキテクチャ)を設計する(基本設計/外部設計に相当) | | ソフトウェア詳細設計プロセス | モジュール内部のロジックを設計する(詳細設計/内部設計に相当) | | ソフトウェア構築プロセス | プログラムをコーディングする | | ソフトウェア統合プロセス | モジュールを結合する(結合テストを含む) | | ソフトウェア適格性確認テストプロセス | ソフトウェアが要求を満たすかテストする |
##### 6. ソフトウェア支援プロセス(Software Support Processes) ソフトウェア開発を横断的に支えるプロセスです。 | プロセス | 内容 | |---|---| | ソフトウェア文書化管理プロセス | 文書の作成・管理 | | ソフトウェア構成管理プロセス | ソースコード等の版管理 | | ソフトウェア品質保証プロセス | ソフトウェアの品質保証 | | ソフトウェア検証プロセス | 仕様適合性の確認 | | ソフトウェア妥当性確認プロセス | 利用者要求適合性の確認 | | ソフトウェアレビュープロセス | レビューの実施 | | ソフトウェア監査プロセス | 標準・手順への準拠監査 | | ソフトウェア問題解決プロセス | 不具合等の分析・解決 |
##### 7.ソフトウェア再利用プロセス(Software Reuse Processes) | プロセス | 内容 | |---|---| | ドメインエンジニアリングプロセス | 特定分野向けの再利用可能な資産を開発する | | 再利用資産管理プロセス | 再利用資産の登録・管理を行う | | 再利用プログラム管理プロセス | 組織的な再利用の推進・計画を行う |
  • 検証 (Verification) : 「仕様どおりに正しく作られているか」を確認する
  • 妥当性確認 (Validation) : 「利用者にとって正しいものが作られているか」を確認する
  • 修整 (テーラリング) : プロジェクト計画時、及び契約締結前に、プロジェクトの規模・種類・契約形態に合わせてライフサイクルプロセスを最適化する
    ※ 発注者・受注者双方の合意のもとで実施し、契約トラブル(「言った/言わない」問題)を防ぐ必要がある
  • リファクタリング : 外部から見た振る舞い(機能)を変えずに、内部のソースコード構造を整理・改善する作業
    • 可読性・保守性の向上
    • バグの予防

    例

    • メソッドの抽出 : 長い処理の一部を切り出し、意味のある名前のメソッドにする
    • 変数名・メソッド名の変更 : 意図が伝わる名前に変更し可読性を高める
    • 重複コードの統合 : 同じ処理を共通化し、単一箇所で管理できるようにする
    • クラスの分割・統合 : 責務が肥大化したクラスを分割し、単一責任にする
    • 条件式の単純化 : 複雑な条件分岐を整理し、意図を明確にする

開発モデル

| モデル名 | 特徴 | メリット | デメリット | |---|---|---|---| | ウォーターフォールモデル |
  1. 要件定義
  2. 設計
  3. 実装
  4. テスト
  5. 運用
を**順番に**進める

  • 後戻りしない前提の開発モデル
  • 各工程の成果物を明確にする
  • 工程完了後(レビューで確認後)に次工程へ進む
|
  • 進捗管理がしやすい
  • 大規模開発で工程の分業がしやすい
|
  • 手戻りコストが大きい
  • 途中の仕様変更に弱い
| | V字モデル |
  • ウォーターフォールモデルを拡張したモデル
  • 開発工程とテスト工程をV字型で対応付ける
対応関係
  • 要件定義 ⇔ 受入テスト
  • 設計 ⇔ システムテスト
  • 実装 ⇔ 単体テスト
|
  • 各開発工程に対応するテスト工程が明確
  • テストの抜け漏れを防ぎやすい
  • 品質保証がしやすい
|
  • ウォーターフォールと同様、手戻りに弱い
| | プロトタイピングモデル |
  • 開発の早い段階で試作品(プロトタイプ)を作成する
  • 利用者の確認を得ながら開発を進める
|
  • 早期にユーザーレビューを得られる
  • 要件の認識齟齬を早期に発見できる
|

  • 大規模開発には不向き
| | エボリューショナルモデル
(進化型モデル)

  • 試作を重ねながら要件を明確化する
  • プロトタイピングを繰り返し、段階的に完成度を高める
  • システムを進化させていく
|
  • 要件が不明確な開発でも対応しやすい
|
  • 開発の終了時期が見えにくい
  • 全体管理が難しい
| | RAD
(Rapid Application
Development) |

|
  • 開発期間を大幅に短縮できる
|

| | スパイラルモデル |
  • システムを複数のサブシステムに分割する
  • サブシステムごとに段階的に完成度を高める

|
  • 管理が複雑になりやすい

サイクル
  1. テスト作成

**TDDを発展させた手法** |
  • システムの**ふるまい**(仕様)を起点に開発する
  • 開発者・テスト担当者・業務担当者が共通の言葉で仕様を記述する
シナリオの記述形式(Gherkin記法)
  1. Given(前提条件)
  2. When(操作・イベント)

|

  • 仕様書がそのままテストになる

  • 関係者の協力体制が必要
| | スクラム

**アジャイル開発手法**の一つ |
  • 短期間(単位:スプリント)で開発を繰り返す
  • その都度、成果物をレビュー・改善する
スクラムチームの役割
  • プロダクトオーナー(責任:作成するプロダクト)
  • スクラムマスター(責任:プロジェクトの推進)
  • 開発チーム
開発サイクル
  1. スプリントプランニング(計画)
  2. デイリースクラム(毎日の確認)
  3. スプリントレビュー(成果物の確認)
  4. スプリントレトロスペクティブ(振り返り)
主な成果物(アーティファクト)
  • **プロダクトバックログ**
    • プロダクトに必要な要求・機能・改善点を並べた一覧
    • 優先順位順に並べる
    • プロダクトオーナーが管理する
    • 要件の変化に応じて随時見直す(バックログリファインメント)
  • **スプリントバックログ**
    • プロダクトバックログから、今回のスプリントで実施する項目を選んだもの
    • スプリントプランニングで決定する
    • 開発チームが管理する
  • **インクリメント**
    • スプリントで完成した、利用可能な成果物
|
  • チームの自己組織化が進む
  • 進捗の可視化がしやすい
  • 優先度の高い項目から着手できる
|
  • チームの成熟度に成果が左右される
  • プロダクトバックログの優先順位付けが不適切だと価値が出にくい
| | カンバン
(トヨタ手法)

**アジャイル開発の手法**の一つ |
  • 作業の流れ(フロー)をカンバンボードで可視化する
  • 固定のイテレーション(期間)を持たない
  • 仕掛り中の作業数を制限する(WIP制限)
ボードの列の例
  1. 未着手(ToDo)
  2. 作業中(Doing)
  3. 完了(Done)
|
  • ボトルネックを発見しやすい
  • 導入が容易で、既存の進め方を変えずに始められる
|

| | リーン開発 |
  • トヨタ生産方式の考え方をソフトウェア開発に応用する

7つの原則
  1. ムダをなくす
  2. 品質を作り込む
  3. 知識を作り出す
  4. 決定を遅らせる
  5. 速く提供する
  6. 人を尊重する
  7. 全体を最適化する
|
  • 開発のムダを削減できる
  • 価値の高いものに集中できる

  • 考え方が中心で、具体的な手順は別途必要
| | リーンスタートアップ |

  • 反応に応じて方向転換(ピボット)する
サイクル

| | FDD
(フィーチャ駆動開発)

**アジャイル開発手法**の一つ |
  • 顧客にとって価値のある**機能(フィーチャ)**を単位に開発する
  • 機能は小さく、短期間(2週間以内)で完成できる粒度にする
5つのプロセス
  1. 全体モデルの作成
  2. フィーチャリストの作成

  4. フィーチャごとの設計
  5. フィーチャごとの構築
|

  • 熟練した主プログラマの存在に依存する
| | インクリメンタルモデル |
  • システムを機能単位に分割する

機能ごとの繰り返し
  1. 設計

| | DevOps |
  • 開発(Development)と運用(Operations)が連携する

自動化されたパイプライン
  1. ビルド

**DevOpsの中核となるプラクティス** | **CI(継続的インテグレーション)**
  • コードの変更を頻繁に共有リポジトリへ統合する
  • 統合のたびに自動でビルド・テストを実行する
**CD(継続的デリバリ / 継続的デプロイ)**
  • 継続的デリバリ:いつでも本番にリリースできる状態を保つ(本番反映は人が承認)
  • 継続的デプロイ:テスト通過後、本番まで自動でリリースする
|
  • 問題を早期に発見できる
  • リリース作業の手間とミスを減らせる
|
  • 自動テストの整備が必要
  • パイプラインの構築・保守コストがかかる

(Infrastructure as Code)

**DevOpsを支える手法** |

代表的なツール
  • Terraform

|

  • 静的解析(SAST)

  • 誤検知への対応が負担になる場合がある

  • Googleが提唱した、サービスの信頼性を確保するための運用手法
  • 運用の課題をソフトウェアエンジニアリングで解決する
主な考え方
  • SLI(指標)・SLO(目標)を定めて信頼性を数値で管理する
  • エラーバジェット(許容できる障害量)の範囲内で新機能を開発する
  • トイル(手作業の繰り返し)を自動化して削減する
  • ポストモーテム(障害の振り返り)を責めずに行う

  • 運用の自動化が進む

  • 運用とソフトウェア開発の両方に強い人材が必要

**SRE・DevOpsで用いられる手法** |
  • 本番(または本番に近い)環境で、意図的に障害を発生させる
  • システムが障害に耐えられるか実験して検証する
  • Netflixの「Chaos Monkey」が有名
障害の例
  • サーバやコンテナの停止
  • ネットワーク遅延・切断
  • 負荷の急増
実験の進め方
  1. 定常状態(正常な状態)を定義する
  2. 「障害が起きても定常状態を保てる」という仮説を立てる
  3. 障害を注入する
  4. 仮説どおりか結果を検証する
  5. 弱点を改善する
|
  • 障害耐性の弱点を、実際の障害の前に発見できる
  • 障害対応力と運用体制を鍛えられる
|
  • 本番環境に影響を与えるリスクがある
  • 監視体制・自動復旧など、前提となる基盤が必要
  • 組織の理解と合意が必要
