サーバの構築手順

Nginx (CGI)

必要なパッケージのインストール

##### ※注意 - Python 3.12 以降では `cgi` `cgitb` モジュールが削除されています **古い** CGIスクリプトは動作しないため、 **環境変数** と **stdin** を使ったフォーム処理に書き換える必要があります → **代替モジュール** [`libcgipy`](https://pypi.org/project/libcgipy/) を作成しました

ターミナル 
sudo apt install nginx fcgiwrap
pip install libcgipy    # Pythonスクリプトを動かす場合

設定ファイルの編集

ターミナル 
sudo nano /etc/nginx/sites-available/[Project Name]

エディタ 
server {
    listen 80;
    server_name radicon.lan;

    location /cgi-bin/ {
        gzip off;
        alias [path]/cgi-bin/;
        fastcgi_pass unix:/run/fcgiwrap.socket;
        include /etc/nginx/fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $request_filename;
        fastcgi_param PATH_INFO $fastcgi_path_info;
    }
}

設定の変更

ターミナル 
sudo ln -s /etc/nginx/sites-available/[Project Name] /etc/nginx/sites-enabled/
sudo rm /etc/nginx/sites-enabled/default
sudo nginx -t # テスト

アプリの設定

ターミナル 
cd [Project Name]

バッチファイル (.bat) 
@echo off

if "%1" == "" (
    goto help

) else if "%~1" == "/?" (
    goto help

) else if "%~1" == "-help" (
    goto help

) else if "%~1" == "-app" (
    if "%2" == "" (
        echo アプリ作成
        set /p appName="アプリ名 : "
    ) else (
        set appName=%2
    )
    setlocal enabledelayedexpansion
    python manage.py startapp !appName!
    echo 完了しました
    pause > nul
    exit /b

) else if "%~1" == "-mig" (
    if "%2" == "" (
        echo マイグレーション
        set /p appName="アプリ名 : "
    ) else (
        set appName=%2
    )
    setlocal enabledelayedexpansion
    python manage.py makemigrations !appName!
    python manage.py migrate
    echo 完了しました
    pause > nul
    exit /b

) else if "%~1" == "-run" (
    python manage.py runserver
    pause>nul
    exit /b

) else if "%~1" == "-col" (
    python manage.py collectstatic
    pause>nul
    exit /b

) else if "%~1" == "--create-admin" (
    python manage.py createsuperuser
    pause>nul
    exit /b

) else (
    echo 引数が違います
    goto help
)

:help
    echo %~0
    echo [/?]             : help
    echo [-app] [appName] : 指定したアプリを作成
    echo [-mig] [appName] : 指定したアプリのマイグレーションを実行
    echo [-run]           : ローカルサーバ立ち上げ
    echo [-col]           : staticファイルを集める
    echo [--create-admin] : 管理者登録
    cmd
    exit /b

WantedBy=multi-user.target

sudo systemctl daemon-reload

Djangoのセキュリティ機能

| Djangoセキュリティ機能 | 有効方法 | 対策する脆弱性 | | --- | --- | --- | | CSRF対策用トークンの
  • 発行
  • HTMLへの埋め込み
  • 必要な紐づけ(アカウント・セッションオブジェクト)
  • リクエスト時の検証
|
  • `MIDDLEWARE` に `django.middleware.csrf.CsrfViewMiddleware` (startproject時のデフォルトで有効)
  • POSTフォームに `{% csrf_token %}`
  • AJAXは `X-CSRFToken` ヘッダでトークンを送信
  • 信頼するオリジンは `CSRF_TRUSTED_ORIGINS`
| CSRF (クロスサイトリクエストフォージェリ) | | テンプレートの自動エスケープ |
  • デフォルトで有効 (設定不要)
  • 無効化するのは `safe` フィルタ・`mark_safe()`・`{% autoescape off %}` (使用は最小限に)
  • JSへ値を渡す場合は `json_script` フィルタ
| XSS (クロスサイトスクリプティング) | | ORMによるSQLのパラメータ化 |
  • `filter()` / `get()` などORMを使う (デフォルトで有効)
  • 生SQLは `raw()` / `cursor.execute()` の第2引数でパラメータを渡す (文字列結合・f文字列は使わない)
| SQLインジェクション | | クリックジャッキング対策ミドルウェア |
  • `MIDDLEWARE` に `django.middleware.clickjacking.XFrameOptionsMiddleware` (デフォルトで有効)
  • `X_FRAME_OPTIONS = "DENY"` (デフォルト)または `"SAMEORIGIN"`
  • ビュー単位は `@xframe_options_deny` / `@xframe_options_sameorigin` など
| クリックジャッキング | | HTTPSリダイレクト |
  • `MIDDLEWARE` に `django.middleware.security.SecurityMiddleware`
  • `SECURE_SSL_REDIRECT = True`
  • リバースプロキシ配下では `SECURE_PROXY_SSL_HEADER` も設定
| 通信の盗聴・改ざん (中間者攻撃) | | HSTS (Strict-Transport-Security ヘッダ) |
  • `SECURE_HSTS_SECONDS = 31536000` など
  • `SECURE_HSTS_INCLUDE_SUBDOMAINS = True`
  • `SECURE_HSTS_PRELOAD = True`
| SSLストリッピング (HTTPSへのダウングレード攻撃) | | Cookieの保護属性 |
  • `SESSION_COOKIE_SECURE = True`
  • `CSRF_COOKIE_SECURE = True`
  • `SESSION_COOKIE_HTTPONLY = True` (デフォルト)
  • `SESSION_COOKIE_SAMESITE = "Lax"` (デフォルト)
| セッションハイジャック、Cookieの盗聴・窃取 (XSS経由含む)、CSRF | | MIMタイプスニッフィング防止 (X-Content-Type-Options) | `SECURE_CONTENT_TYPE_NOSNIFF = True` (デフォルトで有効、`SecurityMiddleware` が付与) | MIMスニッフィングによる意図しないスクリプト実行 | | Referrer-Policy ヘッダ | `SECURE_REFERRER_POLICY = "same-origin"` (デフォルト) | Refererヘッダ経由のURL・情報漏えい | | Cross-Origin-Opener-Policy ヘッダ | `SECURE_CROSS_ORIGIN_OPENER_POLICY = "same-origin"` (デフォルト) | クロスオリジンのウィンドウ経由の攻撃 (Spectre系のサイドチャネルなど) | | Content Security Policy (Django 6.0以降) |
  • `MIDDLEWARE` に `django.middleware.csp.ContentSecurityPolicyMiddleware`
  • `SECURE_CSP` でポリシーを定義
| XSS、不正なリソース読み込み、データ流出 | | Hostヘッダの検証 |
  • `ALLOWED_HOSTS = ["example.com"]`
  • `DEBUG = False` では必須
| HTTP Hostヘッダ攻撃 (パスワードリセットポイズニング、キャッシュポイズニング) | | パスワードのハッシュ化 |
  • `PASSWORD_HASHERS` (デフォルトはPBKDF2 + ソルト)
  • Argon2・bcryptも選択可能 (追加パッケージが必要)
| パスワード漏えい時の平文流出、レインボーテーブル・総当たり攻撃 | | パスワードバリデーション | `AUTH_PASSWORD_VALIDATORS` (最小長・よくあるパスワード・数字のみ・ユーザー属性との類似を検査) | 弱いパスワード、辞書攻撃 | | セッション管理 |
  • `django.contrib.sessions` と `SessionMiddleware`
  • ログイン時にセッションキーを再生成 (自動)
  • `SESSION_COOKIE_AGE` で有効期限を調整
| セッション固定攻撃、セッションIDの推測 | | 認証・認可のデコレータ/Mixin |
  • `@login_required` / `LoginRequiredMixin`
  • `@permission_required` / `PermissionRequiredMixin`
  • `@user_passes_test`
| 認証・認可の不備 (アクセス制御の欠陥) | | 署名機能 |
  • `django.core.signing` (`Signer` / `TimestampSigner` / `dumps` / `loads`)
  • `SECRET_KEY` を秘匿して使用
| データの改ざん | | パスワードリセットトークン |
  • `PasswordResetView` など組み込みビューを利用
  • トークンは有効期限付き (`PASSWORD_RESET_TIMEOUT`)で、比較には定数時間比較を使用
| トークン推測・再利用、タイミング攻撃 | | オープンリダイレクト対策 |
  • `url_has_allowed_host_and_scheme()` でリダイレクト先を検証
  • `LoginView` の `next` パラメータは自動で検証
| オープンリダイレクト | | ファイルアップロードの保護 |
  • `FileField` / `ImageField` (Pillowによる画像検証)
  • `FileExtensionValidator` で拡張子を制限
  • `DATA_UPLOAD_MAX_MEMORY_SIZE` / `DATA_UPLOAD_MAX_NUMBER_FIELDS` / `FILE_UPLOAD_PERMISSIONS`
  • ファイル名は自動サニタイズ (`get_valid_filename`)
| ディレクトリトラバーサル、任意ファイルの設置、リソース枯渇 (DoS) | | ヘッダインジェクション対策 | メール送信 (`send_mail` など)や `HttpResponse` のヘッダに改行コードが含まれると例外を送出 (自動) | HTTP/メールヘッダインジェクション | | フォームバリデーション |
  • `forms.Form` / `ModelForm`
  • `ModelForm` では `fields` を明示 (`__all__` は避ける)
| 不正入力、マスアサインメント | | デバッグ情報・本番設定の保護 |
  • 本番では `DEBUG = False`
  • `SECRET_KEY` は環境変数などで管理
  • `python manage.py check --deploy` で設定を診断
| 内部情報の漏えい、設定不備 |

- 「デフォルトで有効」と書いた項目も、`startproject` が生成する `settings.py` を前提にしています。`MIDDLEWARE` から該当行を消していないか確認してください。 - ログイン試行回数の制限 (ブルートフォース対策)はDjango本体には含まれません。`django-axes` や `django-ratelimit` などの追加パッケージで対応します。 - 本番リリース前は `python manage.py check --deploy` で、上記設定の不足を一括チェックできます。 - 設定名や既定値はバージョンで変わることがあるため、使用中のバージョンの公式ドキュメント (Security in Django / Deployment checklist)も併せて確認してください。
