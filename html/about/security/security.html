TLS (Transport Layer Security) / SSL (Secure Sockets Layer)

TCP等の通信経路上でデータを暗号化し、盗聴・改ざん・なりすましを防ぐためのプロトコル
Netscape社が考案したSSLが起源で、後にIETFにより標準化され「TLS」と改称された
現行のSSLはすべて非推奨・廃止されており、実質的にTLSのみが利用されているが、慣習的に「SSL」「SSL/TLS」と併記されることも多い

提供する機能

  • 機密性 : 共通鍵暗号によるデータの暗号化
  • 完全性 : MAC(メッセージ認証符号)による改ざん検知
  • 認証 : デジタル証明書によるサーバ
    (および必要に応じクライアント)の身元確認

### TLS関連用語 | 用語 | 内容 | |---|---| | DTLS (Datagram TLS) |
  • UDP等のコネクションレス(データグラム型)通信に、
    TLSと同等のセキュリティ(暗号化・完全性保護・認証)を提供するプロトコル
  • パケットの損失対策 : 再送タイムアウト
  • 順序入れ替わり対策 : シーケンス番号(epoch含む)を付与する
  • リフレクション攻撃対策 : ハンドシェイク開始時にHelloVerifyRequestを用いて送信元IPアドレスの検証
| | QUICTLS
(QUIC-TLS) |
  • QUIC(RFC 9000)が、TLS 1.3(RFC 8446)をハンドシェイクと鍵共有に利用する仕組み(RFC 9001)
  • TLSレコードプロトコルは使わず、TLSハンドシェイクメッセージをQUICの`CRYPTO`フレームで運ぶ
  • TLSで合意・導出した鍵を、QUICがパケット単位の暗号化(AEAD)とヘッダ保護に使用する
  • TLS 1.3のみ対応(TLS 1.2以前は使用不可)
  • 転送(QUIC)と暗号(TLS)のハンドシェイクを統合し、1-RTTで接続確立(再接続時は0-RTTも可能)
  • 補足 : 「quictls」はQUIC向けAPIを追加したOpenSSLのフォークの名称でもある
| | TLSアクセラレータ | TLSの暗号化・復号処理を専用ハードウェアで肩代わりし、サーバの処理負荷を軽減する装置 | | ハンドシェイクプロトコル
(Handshake Protocol) | TLSにおいて、通信開始時に暗号方式の合意・サーバ(および必要に応じクライアント)の認証・鍵交換を行う上位プロトコル
この過程でプリマスタシークレット・マスターシークレットが生成される | | プリマスタシークレット
(Pre-Master Secret) | TLSハンドシェイクの鍵交換(DHE/ECDHE等)によって
クライアント・サーバ間で共有される元となる乱数値
この値をもとにマスターシークレットが導出される | | マスターシークレット
(Master Secret) | プリマスタシークレットとクライアント/サーバの乱数(Random)から、
擬似乱数関数(PRF)を用いて生成される48byteの値
暗号化鍵・MAC鍵・IV等、実際に使用する鍵材料はここから導出される | | レコードプロトコル
(Record Protocol) | TLSにおいて、ハンドシェイクプロトコルで確立された鍵を用いて
実際のアプリケーションデータの暗号化・完全性保護・送受信を行う下位プロトコル |

QUICTLS認証手順

  • QUICTLSでは、TLS 1.3のハンドシェイクをQUICパケットの中で行う
  • TCPの3ウェイハンドシェイクとTLSハンドシェイクが統合されるため、最短1-RTTで暗号化通信を開始できる
  • ※ 1-RTT(往復回数) : ハンドシェイク完了までに必要な往復が1回であること
  • ※ 1-RTT(鍵・パケット名) : ハンドシェイク完了後に使うアプリケーション用鍵、およびそれで保護するShort Headerパケット

マルウェア感染発覚後の対応

ステップ 担当 行動
フェーズ1: 初動(触らない・隔離する・連絡する)
1 発見者(一般ユーザー) 端末を操作せず、電源を切らない
シャットダウン・再起動・ウイルス駆除ソフトの実行はしない(メモリ上の証拠が消えるため)
※ランサムウェアの場合の例外は、表の下の注意を参照
2 発見者(一般ユーザー)
※EDRがあればCSIRT		 ネットワークから切り離す
LANケーブルを抜く、Wi-Fiを無効化する(電源は入れたまま)
EDRによる隔離機能がある場合はCSIRTが遠隔隔離する
3 発見者(一般ユーザー) 情報システム部門/CSIRTへ報告する
発見日時、症状、直前の操作、画面表示(スマートフォン等で撮影)を伝える
フェーズ2: 証拠保全(揮発性の高いものから順に取得)
4 CSIRT/情報システム部門 インシデントとして対応を開始し、記録を始める
対応体制を立ち上げ、「いつ・誰が・何をしたか」の時系列記録を開始する
判断に迷う場合は専門業者へ連絡する
5 CSIRT/専門業者(フォレンジック) 揮発性データを取得する
メモリダンプ、ネットワーク状態(ルーティングテーブル、ARPキャッシュ、接続中セッション、待ち受けポート)、プロセス一覧を取得する
6 CSIRT/専門業者(フォレンジック) ディスクイメージを取得する
書き込み防止措置を行って複製し、ハッシュ値を記録する
証拠の受け渡しは Chain of Custody で管理する
フェーズ3: 被害範囲の特定・封じ込め
7 CSIRT/システム管理者 被害範囲を特定し、認証情報を無効化する
他端末への横展開、外部への通信、情報漏洩の有無をログ(プロキシ/FW/EDR)で確認する
対象ユーザーのパスワード変更、トークン・セッションの失効を行う
フェーズ4: 駆除・復旧(証拠保全の完了後)
8 システム管理者 マルウェアを駆除し、システムを修復する
駆除・修復が困難な場合は、OSごと初期化し、感染前の健全なバックアップからデータを復元する
9 システム管理者 再スキャンと監視強化を行う
パターンファイル(シグネチャ)を最新化して全体をスキャンし、他の感染や残存がないか確認する
復旧後しばらくは監視を強化する
フェーズ5: 再発防止・対外対応
10 CSIRT/専門業者 根本原因を調査し、再発防止策を実施する
感染経路・原因を分析し、パッチ適用、教育、ルール見直し等を行う
11 経営層/法務/広報
(CSIRTが支援)		 必要に応じて対外対応を行う
個人情報漏洩のおそれがある場合は個人情報保護委員会への報告、取引先・本人への通知、警察への相談を検討する
※手順4の時点から並行して判断を始める
注意(ランサムウェアの場合)
まずステップ2のネットワーク切断を最優先で行う
切断後も端末内で暗号化が続いている場合に限り、被害拡大の防止を優先して、次の対応を検討する
状況(ステップ2の後) 対応
暗号化が止まっている・進行していない 電源は維持し、ステップ3以降へ進む
暗号化が続いている 休止状態にする(メモリがディスクに書き出され、証拠が残りやすい)
困難なら電源断も検討する(メモリ上の証拠は失われる)
判断は現場で行わず、CSIRTまたは専門業者の指示に従う
連絡が取れず被害が拡大し続ける場合のみ、やむを得ない措置として上記を行う
