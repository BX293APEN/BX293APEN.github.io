(XML Signature) | 署名規格
(W3C勧告) | XML文書(全体・一部の要素・外部リソース)に対するデジタル署名の標準規格

1対1・1対多といった数の関係は形式ではなく<Reference>の数で決まる

主な構成要素 :
  • <SignedInfo> : 署名対象の情報のまとまり(実際に署名される要素)
  • <Reference> : 署名対象1件分の参照(URI、Transforms、DigestMethod、DigestValue)。複数指定可
  • <SignatureValue> : <SignedInfo>に対する署名値
  • <KeyInfo> : 検証用の公開鍵・証明書(省略可)
  • <Object> : エンベロピング署名で対象データを格納する要素

  3. <SignedInfo>を正規化し、秘密鍵で署名して<SignatureValue>を生成する
  4. <KeyInfo>を付与し、<Signature>要素を形式に応じた位置に配置する
  5. 検証時はDigestValueの再計算と、SignatureValueの公開鍵による検証の両方を行う

    • 全通信が経由するため性能要件が高い
    • プロキシが単一障害点・ボトルネックになりやすい

  • メリット : 既存システムの改修がほぼ不要で、

    認証情報の保管(暗号化等)

**フェデレーション型(ID連携)**

**PFS(Perfect Forward Secrecy : 前方秘匿性)**
  • 長期鍵(サーバの秘密鍵等)が将来漏洩しても、
    過去に交換したセッション鍵・通信内容が復元されない性質
  • セッションごとに一時的な鍵ペア(Ephemeral鍵)を生成し、
    通信終了後に破棄することで実現する
  • 同じ鍵ペアを使い回す静的(Static)なDH/ECDHでは実現できない
    (長期鍵の漏洩により過去の全セッションが復元される)


**量子鍵配送(QKD)の補足**
  • QKDは「鍵を安全に共有する」技術であり、データの暗号化自体は別途AESやワンタイムパッド等で行う
  • 量子状態は測定すると乱れるため、盗聴があると誤り率が上昇し、検知できる
  • 古典チャネルの認証が別途必要
    (事前共有鍵やPQC署名等を用いる。認証が破られると中間者攻撃を受ける)
  • 専用の量子通信機器が必要で、光ファイバでは通信距離や鍵生成速度に制約がある
  • 実機の検出器等を狙う実装攻撃(サイドチャネル)が課題
  • デコイ状態法は個別のプロトコルではなく、弱いコヒーレント光を使う実システムで光子数分離攻撃(PNS攻撃)を防ぐ技術
    (BB84等と組み合わせて用いる)
  • 数学的困難性に基づく耐量子計算機暗号(PQC)とは別系統で、両者を併用する考え方もある

TLS (Transport Layer Security) / SSL (Secure Sockets Layer)

TCP等の通信経路上でデータを暗号化し、盗聴・改ざん・なりすましを防ぐためのプロトコル
Netscape社が考案したSSLが起源で、後にIETFにより標準化され「TLS」と改称された
現行のSSLはすべて非推奨・廃止されており、実質的にTLSのみが利用されているが、慣習的に「SSL」「SSL/TLS」と併記されることも多い

提供する機能

  • 機密性 : 共通鍵暗号によるデータの暗号化
  • 完全性 : MAC(メッセージ認証符号)による改ざん検知
  • 認証 : デジタル証明書によるサーバ
    (および必要に応じクライアント)の身元確認

フォワードプロキシ クライアント側(組織内)とインターネットの間 クライアント 悪意あるサーバ(マルウェア配布サイト・フィッシングサイト・C2サーバ等) URLフィルタリング、マルウェアスキャン、クライアントの隠蔽、ログ取得、キャッシュ
リバースプロキシ サーバ側(DMZ・クラウドの入口) サーバ 悪意あるクライアント(攻撃者) サーバの隠蔽、WAF連携、TLS終端、負荷分散、キャッシュ
メールプロキシ メールサーバの前段 メールサーバ・利用者 スパム・ウイルス・フィッシングメール、情報漏えい 受信メールの検査、送信元の検証、送信メールの検査
RBI クラウド等の隔離環境
(プロキシ/SWGから振り分けることが多い)		 クライアント(ブラウザ) Web経由のマルウェア感染(ドライブバイダウンロード・ゼロデイ攻撃等) ブラウザを隔離環境で実行し、画面のみを端末へ転送
VDI データセンター・クラウド上の仮想デスクトップ 端末とデータ(デスクトップ全体) マルウェア感染、端末の紛失・盗難による情報漏えい デスクトップ環境をサーバ側で実行し、画面のみを端末へ転送
URLフィルタリング
Webフィルタリング 		危険・不要なWebサイトへのアクセスを、URLのレピュテーション情報やカテゴリ分類に基づいて制限する仕組み 制限の対象は、業務上不要・危険なカテゴリのWebサイト(悪意あるサイト、危険なダウンロード元、フィッシングサイト等)
フォワードプロキシ(SWG)やUTM等の機能として実装されることが多い
ブラックリスト方式・ホワイトリスト方式のどちらでも運用できる(「全層によるセキュリティ」を参照)
RBI
Remote Browser Isolation 		Webブラウザを利用者の端末ではなく隔離環境で実行し、端末には画面のみを転送することで、Web経由の脅威を遮断する仕組み Webサイトのスクリプトやコンテンツが端末上で実行されないため、ドライブバイダウンロードやゼロデイ攻撃、フィッシングサイト閲覧による被害を抑えられる
  1. 利用者がURLにアクセスすると、クラウド上等の隔離環境のブラウザがそのサイトを読み込む
  2. Webコンテンツ(スクリプト等)は隔離環境側で実行される
  3. 端末には描画結果(画面の映像、または無害化した描画データ)のみが送られる
  4. 端末でのキーボード・マウス操作は、隔離環境へ送り返される
URLフィルタリングが「許可/ブロック」の二択であるのに対し、RBIは「許可するが隔離して閲覧させる」ことができる
未分類サイトやリスクの高いサイトのみRBI経由に振り分ける運用が多い(プロキシ/SWGと連携)
コピー・貼り付け、ファイルのダウンロード、印刷等はポリシーで制御できる
課題は、操作の遅延、導入コスト、一部サイトの表示互換性
デスクトップ全体を隔離するVDI(「クライアント(エンドポイント)のセキュリティ」を参照)に対し、ブラウザだけを隔離する方式
迷惑メール対策 迷惑メールを判定し、拒否・隔離する方式の総称
単独ではなく、複数を組み合わせて使われる 		ブラックリスト方式
メールでの適用例 		既知の迷惑メール送信元(IPアドレス・ドメイン等)の一覧と照合し、該当するメールを拒否・隔離する
DNSBL(RBL)として公開されているリストを利用することもある
考え方や他の適用例は、「全層によるセキュリティ」のブラックリスト/ホワイトリスト方式を参照
ベイジアンフィルタ 過去の迷惑メール・正常メールの単語出現傾向を学習し、確率的に迷惑メールかどうかを判定する(ベイズの定理を利用)
未知の迷惑メールにも対応でき、利用者ごとに学習させることで精度が向上する
学習データが少ないうちは精度が低く、誤判定も起こりうる
グレーリスティング 未知の送信元からの初回メールを一時的に拒否し、再送してくるかどうかで正規のメールサーバかを判別する
  1. 未知の送信元(IPアドレス・送信者・宛先の組)からの初回の配送を、SMTPの一時エラー(4xx)で拒否する
  2. 正規のメールサーバには再送の仕組みがあるため、一定時間後に再送してくる
  3. 再送を確認できた送信元を許可リストに登録し、以降のメールを受け付ける
再送機能を持たない迷惑メール送信プログラムを排除できる一方、初回の配送が遅れる
送信ドメイン認証
SPF / DKIM / DMARC 		送信元ドメインのなりすましを検知し、正規の送信元からのメールであることを検証する
なりすましメール(フィッシング等)対策の代表技術で、受信側が検証して結果に応じた処理を行う 		SPF
Sender Policy Framework 		送信元ドメインのDNSに登録された正規の送信サーバのIPアドレスと、実際の送信元IPアドレスを照合する
DKIM
DomainKeys Identified Mail 		送信側がメールに電子署名を付与し、受信側がDNSで公開された公開鍵で署名を検証する(メールの改ざんも検知できる)
DMARC
Domain-based Message Authentication,
Reporting and Conformance 		SPF/DKIMの検証結果とFromヘッダのドメインとの整合性に基づき、認証失敗時の扱い(何もしない/隔離/拒否)を送信側が宣言する。認証結果のレポートも受け取れる
多要素認証
MFA 		次の3種類の認証要素のうち、異なる種類を2つ以上組み合わせて認証強度を高める
パスワードと秘密の質問のように、同じ種類(知識情報)を2つ使っても多要素認証にはならない 		知識情報 パスワード・PIN等
所持情報 ワンタイムパスワード生成トークン・ICカード・スマートフォン・USBキー(USBトークン)等
生体情報 指紋・顔・虹彩等
CASB
Cloud Access Security Broker 		クラウドサービスの利用状況を可視化し、セキュリティポリシーを適用・統制する仕組み 利用者とクラウドサービスの間に位置し、許可されていないクラウドサービスの利用(シャドーIT)の検出、機密データのアップロード制限、不審な操作の検知等を行う
自組織が構築したクラウド環境の設定不備を検出するCSPMとは対象が異なる(「全層によるセキュリティ」を参照)
SBOM
Software Bill of Materials 		ソフトウェアを構成するオープンソースライブラリ等のコンポーネント名・バージョン・依存関係を一覧化した部品表 脆弱性が発覚した際の影響範囲の早期特定や、サプライチェーンリスクの管理に利用される
代表的なフォーマットにSPDXやCycloneDXがある

UTM

運用・管理の一元化やコスト削減ができる一方、1台に集中するため障害時の影響が大きく(単一障害点)、全機能を有効にすると処理性能が低下しやすい

IPSは、検知に加えて不正な通信をリアルタイムに遮断する 		IDS ネットワークやホスト上の不正な兆候を検知し、管理者に通知する(通信の遮断はしない)
監視対象により、ネットワーク型の「NIDS」とホスト型の「HIDS」(「クライアント(エンドポイント)のセキュリティ」を参照)に分けられる 		Snort
NIDS
ネットワーク型IDS 		ネットワーク上を流れるパケットを監視し、ネットワークセグメント全体に対する不正アクセスの兆候を検知する
1台のセンサで複数のホストを監視できる一方、暗号化された通信(HTTPS等)の中身は検査できない
IPS IDSの機能に加え、検知した不正な通信をリアルタイムに遮断する機能を持つ

NDR

検疫ネットワーク
検疫ネットワークシステム 		社内ネットワークへの接続前に、パターンファイルの更新状況やパッチ適用状況等、端末のセキュリティ状態を検査する専用の隔離ネットワーク 基準を満たさない端末は、本番ネットワークへの接続を許可しない
  1. 端末が接続しようとすると、まず検疫用の隔離ネットワークに接続させる
  2. OSのパッチやウイルス対策ソフトのパターンファイル等の状態を検査する
  3. 基準を満たさない端末は、隔離環境で修復(パッチ適用・パターンファイル更新等)する
  4. 基準を満たしたことを確認してから、本番ネットワークへの接続を許可する
ZTNA
ゼロトラストネットワークアクセス 		「何も信頼しない」ことを前提に、通信のたびにアクセス主体(ユーザ・デバイス)を検証・認可する仕組み 従来のVPNが接続後に社内ネットワーク全体へアクセスできてしまいがちなのに対し、許可されたアプリケーションにのみ接続させる
DDoS対策 大量の通信によるサービス停止攻撃に対する耐性を高める DDoS対策サービス
スクラビングサービス 		大量トラフィックを専用設備(スクラビングセンタ)で吸収・選別し、正常な通信のみをオリジンサーバへ転送する
DNSの切り替えやBGP経路の広告により、通信をスクラビングセンタへ迂回させる
CDN
コンテンツデリバリネットワーク 		コンテンツを世界各地のエッジサーバに分散配置(キャッシュ)し、利用者に近いサーバから配信する
負荷分散やDDoS攻撃に対する耐性を高められる
エッジサーバがリバースプロキシとして応答するため、オリジンサーバを直接公開せずに済む
DNSSEC DNS応答に電子署名を付与し、DNSキャッシュポイズニング等の改ざんを検知可能にする仕組み 権威DNSサーバが署名し、キャッシュDNSサーバ(フルサービスリゾルバ)が検証する
応答の真正性・完全性を確認できるが、通信内容の暗号化(秘匿)は行わない

  • バックスキャッター: 送信元を詐称したDDoS攻撃の被害ホストが返した応答パケット

クライアント(エンドポイント)のセキュリティ

サービス 概要 種類 説明 製品例
アンチウイルスソフト 既知のマルウェアのパターン(シグネチャ)や挙動を検知・駆除するソフトウェア
検知手法の違いにより、右の方式に分けられる(組み合わせて使われる) 		パターンマッチング法
シグネチャ法 		既知のマルウェアの特徴的なコードパターン(シグネチャ)をデータベース化し、検査対象と照合して検知する
既知のマルウェアには有効だが、未知のマルウェア(ゼロデイ攻撃等)には対応できない
パターンファイルを常に最新に保つ必要がある
ヒューリスティック法 マルウェアに共通する特徴的なコード構造・命令列・動作を経験則(ルール)に基づいて評価し、疑わしさの度合いで悪意の有無を判定する
  • シグネチャ(パターンファイル)に依存しないため、未知のマルウェアや既存マルウェアの亜種にも対応可能
  • 正常なプログラムを誤って不正と判定する「フォールスポジティブ」が起こりやすい
  • 検査方法により「静的ヒューリスティック」と「動的ヒューリスティック」に大別される(下表)
項目 静的ヒューリスティック 動的ヒューリスティック
実行の有無 実行しない(コードそのものを解析する) 実行する(エミュレータ等の仮想環境で動作させる)
検査内容 逆アセンブル等で命令列・API呼び出し・文字列を調べ、マルウェア特有のコードパターンがないかを評価する ファイル操作・レジストリ変更・不審な通信など、実行時の振る舞いを評価する
利点 実際に実行しないため安全で、検査も高速 難読化されたコードでも、実行時に現れる挙動から検知できる
欠点 難読化・パッキング・暗号化されたコードは解析しにくく、検知を回避されやすい 実行のため処理に時間がかかり、仮想環境を検知して悪意ある動作を行わないマルウェアには検知を回避されることがある
動的ヒューリスティックは、ビヘイビア法(振る舞い検知)に近い考え方
ビヘイビア法
振る舞い検知 		プログラムを実際に、または模擬環境(サンドボックス)で動作させ、その挙動(不審なファイル操作・通信等)を監視して悪意の有無を判定する
未知のマルウェアにも対応可能
コンペア法 検査対象ファイルを、あらかじめ保管しておいた原本(感染前のクリーンな状態のファイル)と比較し、差異の有無から感染を判定する
原本を安全に保管・管理する必要があり、正規の更新による変更との区別も必要になる
チェックサム法
インテグリティチェック法 		ファイルのハッシュ値(チェックサム)をあらかじめ算出・保管しておき、定期的に再計算した値と比較することで改ざんや感染の有無を検知する
原本全体を保管するコンペア法に比べ、保管するデータが小さくて済む
ハッシュ値自体を攻撃者に書き換えられないよう、安全な場所に保管する必要がある
EDR
Endpoint Detection and Response 		エンドポイント(PC・サーバ)上の挙動を監視し、侵害の検知・調査・封じ込め(端末のネットワーク隔離等)を行う仕組み プロセス・ファイル操作・通信等の挙動を継続的に監視・記録する
アンチウイルス等の入口対策をすり抜けた脅威への対応(侵入後の対策)に有効
HIDS
ホスト型IDS 		サーバやPC等、個々のホスト上にエージェントを常駐させ、ログの改ざんやファイルの変更、プロセスの異常等を監視する方式 ホスト内部の変化を直接監視できる一方、監視対象ごとにエージェントの導入・管理が必要
DLP
Data Loss Prevention 		機密情報の外部送信・持ち出しを検知・防止する仕組み 機密情報のキーワードやデータ形式・ラベル等に基づいて検知し、メール送信・USBメモリへの書き出し・クラウドへのアップロード等を警告・ブロックする
監視する場所により、エンドポイント型・ネットワーク型(メール/Web)・クラウド型等がある
デバイス制御
USBデバイス制御 		USBメモリ等の外部記憶媒体や周辺機器の接続・利用を、端末上のソフトウェア(エージェント)で制御する仕組み
  • 許可した機器(登録済みのUSBメモリ等)のみ利用を認める(ホワイトリスト方式)
  • 書き込みのみ禁止(読み取り専用)にする等、操作単位で制限する
  • 機器の利用ログを記録する
情報の持ち出しやマルウェアの侵入を防止する
物理的にポートを塞ぐ方法は、「物理層・その他のセキュリティ」のUSBポートロックを参照
PAM
特権アクセス管理 		管理者権限等の特権アカウントの利用を制御・監視・記録する仕組み
  • 特権IDの貸出・払い出しとパスワードの管理(必要なときだけ利用させる)
  • 承認ワークフローによる利用許可
  • 操作ログ・画面操作の記録(証跡の取得)
VDI
Virtual Desktop Infrastructure 		サーバ上の仮想マシンにデスクトップ環境を構築し、利用者の端末からは画面転送プロトコルで操作する仕組み(仮想デスクトップ) アプリケーションやデータは端末ではなくサーバ側にあり、端末とはキーボード・マウス操作と画面情報のみをやり取りする
  • 情報漏えい対策: 端末にデータが残らず、紛失・盗難時の漏えいリスクを下げられる。コピー・貼り付けやファイルの持ち出しもポリシーで制御できる
  • マルウェア対策: 端末が感染しても、業務データのあるサーバ側へ影響が及びにくい。終了時にクリーンな状態へ戻す「使い捨て」の運用もできる
  • 一元管理: OS・アプリケーション・パッチをサーバ側で一括管理できる
  • インターネット分離: インターネット接続用のデスクトップを隔離された環境(VDI)で動かし、手元の端末には画面だけを転送する。プロキシ経由のWeb閲覧を隔離環境で行う形になる
デスクトップ全体を隔離するのがVDI、ブラウザだけを隔離するのがRBI(「アプリケーションによるセキュリティ」を参照)
課題は、サーバ・ネットワークの導入・運用コストと、画面転送による操作の遅延

マルウェア感染発覚後の対応

  1. ネットワークから切り離す
    被害の拡大(他端末への感染拡大や外部への情報送信)を防ぐため、LANケーブルの抜線やWi-Fiの無効化により対象端末を直ちに隔離する
  2. マルウェアの駆除、変更されたシステムの修復
    アンチウイルスソフト等による駆除を行い、改ざんされたファイルや設定を正常な状態に復旧する
  3. PCの初期化、バックアップからの復元
    駆除・修復が困難な場合は、OSごと初期化した上で、感染前の健全なバックアップからデータを復元する
  4. マルウェア対策ソフトの更新、再度のマルウェア検索
    パターンファイル(シグネチャ)を最新の状態に更新した上で、再度全体をスキャンし、他の感染や残存がないかを確認する
  5. 問題の根本原因の調査、セキュリティ対策の改善
    感染経路や原因を分析し、再発防止のための対策(パッチ適用、教育、ルール見直し等)を講じる
