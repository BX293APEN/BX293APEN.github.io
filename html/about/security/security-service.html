└ パケットフィルタリング型
  • 最も基本的な方式
  • 送信元/宛先IPアドレス、ポート番号、プロトコル等のパケットのヘッダ情報のみでルールベースの許可・拒否を判定する
  • OSI参照モデルの第3層(ネットワーク層)・第4層(トランスポート層)で動作する
  • 高速
  • パケットの中身(ペイロード)は検査しない
  • 通信ごとの状態は見ない
  • 戻りパケット用のルールをあらかじめ固定的に開けておく必要がある
 —
└ ダイナミックパケットフィルタリング型
  • ステートフルパケットフィルタリング型とほぼ同一(呼称の違い)
  • 通信の往路(要求)を監視する
  • 通信状況に応じてフィルタリングルールを自動生成する
    • 戻りパケットのみを動的に許可する等
  • 通信が終了したらそのルールを削除する
  • ポートを開けたままにするリスクを減らせる
 —
└ ステートフルパケットフィルタリング型
（ステートフルインスペクションFW）
  • ダイナミックパケットフィルタリング型とほぼ同一(呼称の違い)
  • セッション(コネクション)の状態を管理・追跡する
  • 同一セッションに属する通信のみを許可する
  • なりすましや不正な戻りパケットを排除する
  • 通信の開始から終了までの状態をテーブルで管理する
  • TCPの接続手順等に沿わない通信を遮断する
 —
└ アプリケーションゲートウェイ型
（プロキシ型FW）
  • アプリケーション層(OSI第7層)の内容まで解析する
  • 通信を代理(プロキシ)する
  • 内部と外部の通信を直接つながない
  • クライアント側とサーバ側で別々のセッションを張って中継する
  • 厳密な制御ができる
  • 処理負荷が高い
  • プロトコルごとに対応するプロキシが必要
  • 検査精度が高い
  • プロキシの考え方は「Web・メール防御」のプロキシサーバを参照

  • ネットワークの出入口(ゲートウェイ)に設置する
  • 一括で防御する

    • 全機能を有効にすると処理性能が低下しやすい

IDS（不正侵入検知システム）
IPS（不正侵入防止システム）
  • IDS
    • ネットワークやホスト上の不正な兆候を検知する
    • 管理者に通知する
  • IPSは検知に加えて、不正な通信をリアルタイムに遮断する
  • 判定誤りの評価(フォールスポジティブ・フォールスネガティブ)
    用語特徴利用
    フォールスポジティブ
    （誤検知・過検知）
    • 正常な通信・行為を誤って不正と判定してしまうこと
    • 検知を厳しくすると増える(検知漏れとトレードオフ)
    • 検知システムの判定誤りの評価に使う
    • 以下を招く
      • 業務への影響(正常な通信の遮断)
      • アラート対応による運用負荷の増大
    フォールスネガティブ
    （検知漏れ）
    • 実際には不正な通信・行為であるにもかかわらず正常と判定して見逃してしまうこと
    • 検知を緩くすると増える(誤検知とトレードオフ)
    • 検知システムの判定誤りの評価に使う
    • 被害の直接的な原因となりうる
 —
└ IDS
  • ネットワークやホスト上の不正な兆候を検知する
  • 管理者に通知する
  • 通信の遮断はしない
  • 監視対象により、ネットワーク型の「NIDS」とホスト型の「HIDS」(「エンドポイント防御」を参照)に分けられる
  • 検知方式
    方式判定の基準長所短所
    シグネチャ型(ミスユース検知)
    • 既知の攻撃パターンと照合する
    • 一致したものを不正と判定する(ブラックリスト的)
    		既知の攻撃には確実未知の攻撃には対応できない
    アノマリ型(異常検知)
    • 正常時の状態を基準とする
    • そこから逸脱したものを不正と判定する(ホワイトリスト的)
    		未知の攻撃にも対応できる可能性がある誤検知が起こりやすい

  • 検知方式
    方式判定の基準長所短所
    シグネチャ型(ミスユース検知)
    • 既知の攻撃パターンと照合する
    • 一致したものを不正と判定する(ブラックリスト的)
    		既知の攻撃には確実未知の攻撃には対応できない

  • アノマリ型は誤検知が起こりやすいため、基準の調整・学習段階は通信が止まらないプロミスキャスモード(通知のみ)で運用するのに向く
 Snort
└ IPSインラインモード
  • 通信経路上に直接設置する
  • 通過するすべての通信を検査した上で転送する
  • 不正な通信をリアルタイムに遮断できる
  • 通信経路上にあるため、IPS自体の障害・性能不足が通信全体に影響する(単一障害点)
  • 誤検知した場合の影響：正常な通信まで遮断される。業務への影響が大きい

└ IPSプロミスキャスモード
（パッシブモード）
  • スイッチのミラーポート(SPAN)やタップ等から通信のコピーを受け取って監視する
  • 通信経路上には存在しない
  • 不正な通信そのものを遮断することはできない
  • 検知(IDS的な用途)にとどまる
  • TCPリセットの送信等で接続の切断を試みる製品もある
  • 確実な遮断とはいえない
  • 誤検知した場合の影響：通知が増えるだけで通信は止まらない(IDSも同様)

NDR
（Network Detection and Response）
  • ネットワークトラフィックを分析する
  • 異常な通信パターンや侵害の兆候を検知する
  • 対応を支援する仕組み
  • 次の用途に有効
    • EDRを導入できない機器(IoT・OT機器、未管理の端末等)の監視
    • 侵入後の内部での横展開(ラテラルムーブメント)の検知

検疫ネットワーク
（検疫ネットワークシステム）
  • 社内ネットワークへの接続前に、端末のセキュリティ状態(パターンファイルの更新状況、パッチ適用状況等)を検査する専用の隔離ネットワーク
  • 基準を満たさない端末は本番ネットワークへの接続を許可しない
    1. 端末が接続しようとするとまず検疫用の隔離ネットワークに接続させる
    2. OSのパッチやウイルス対策ソフトのパターンファイル等の状態を検査する
    3. 基準を満たさない端末は隔離環境で修復(パッチ適用・パターンファイル更新等)する
    4. 基準を満たしたことを確認してから本番ネットワークへの接続を許可する
 —
ZTNA
（ゼロトラストネットワークアクセス）
  • 「何も信頼しない」ことを前提とする
  • 通信のたびにアクセス主体(ユーザ・デバイス)を検証・認可する仕組み
  • 従来のVPNとの違い
    方式接続範囲
    従来のVPN接続後に社内ネットワーク全体へアクセスできてしまいがち
    ZTNA許可されたアプリケーションにのみ接続させる
  • SPA(Single Packet Authorization)
    • ポートノッキングの発展形
    • 認証情報を含む暗号化・署名済みの1パケットで認可を行う
    • ZTNAのSDP(Software Defined Perimeter)等で接続制御に使われる
  • ポートノッキングとSPAの違い
    項目ポートノッキングSPA
    認証の仕組み決められたポートへ決められた順序で接続を試みる暗号化・署名された認可パケットを1つ送る
    認証情報ポートの順序(合言葉のようなもの)暗号化・署名されたペイロード
    盗聴・リプレイ攻撃順序を盗み見られると再利用されるタイムスタンプやナンス等で再利用を防げる
    なりすまし・改ざん順序を再現されると防げないHMAC等の署名で検出できる
    実装例knockdfwknop
  • SPAの流れ
    1. サーバは全ポートを閉じ、応答を返さない(外部からは存在しないように見える)
    2. クライアントが認可パケットを1つ送る
    3. サーバはポートを開けずにパケットを受け取り検証する
    4. 検証に成功した送信元IPに限り、指定ポートを一時的に開放する
    5. 一定時間後にルールを自動で削除する

  • 利用者に近いサーバから配信する
  • 負荷分散やDDoS攻撃に対する耐性を高められる

  • オリジンサーバを直接公開せずに済む

DNSSEC
  • DNS応答に電子署名を付与する

  • 応答の真正性・完全性を確認できる
  • 通信内容の暗号化(秘匿)は行わない

CSP
（Content Security Policy）
  • 実行を許可するスクリプトの読み込み元等を指定する
  • XSS等の被害を軽減するHTTPヘッダベースの仕組み
  • WebサーバがContent-Security-Policyレスポンスヘッダでポリシーを通知する
  • ブラウザが許可されていないリソースの読み込み・実行を拒否する

プロキシサーバ
  • クライアントとサーバの間に立つ
  • 通信を代理中継する中継サーバ
  • 設置位置によって守る対象が変わる
    • クライアント側ならクライアント
    • サーバ側ならサーバ
  • 代理中継の考え方はアプリケーションゲートウェイ型FWにも使われる(「ネットワーク防御」のファイアウォールを参照)

└ フォワードプロキシ
  • クライアントの代理として外部のサーバと通信する
  • クライアント側(組織内)とインターネットの間に設置する
  • 悪意あるサーバ(マルウェア配布サイト・フィッシングサイト・C2サーバ等)からクライアントを守る
  • 主な機能
    機能内容
    クライアントの隠蔽
    • 外部サーバにはプロキシのIPアドレスしか見えない
    • クライアントに直接接続されない
    アクセス制御
    • URLフィルタリング・認証により危険・不要なサイトへのアクセスを制限する
    コンテンツ検査
    • ダウンロードされるファイルのマルウェアスキャンや、TLS通信の復号検査(SSLインスペクション)を行う
    ログ取得
    • 誰がどこにアクセスしたかを記録する
    • インシデント調査や監査に利用する
    キャッシュ
    • 同じコンテンツの再取得を省く
    • 帯域を節約する
  • プロキシを迂回する通信は検査できない
  • FWで直接の外部通信を禁止して経由を強制する
  • クラウド型や高機能化したものはSWG(Secure Web Gateway)とも呼ばれる
 Squid
└ リバースプロキシ
  • サーバの代理として外部クライアントからのリクエストを受け付ける
  • 内部のWebサーバ等へ中継する
  • Webサーバ等の前段(DMZやクラウドの入口)に設置する
  • 悪意あるクライアント(攻撃者)からサーバを守る
  • フォワードプロキシとは通信の向きが逆
  • 代理する相手・守る対象が「サーバ側」になる
  • 主な機能
    機能内容
    サーバの隠蔽
    • 内部サーバのIPアドレス・構成・ソフトウェアのバージョン等が外部から見えず、直接攻撃されない
    攻撃の遮断
    • WAF機能と組み合わせる
    • 不正なリクエストを内部サーバへ到達させない
    TLS終端
    • 暗号化・復号をプロキシが代行する
    • サーバの負荷を軽減する
    • 復号後の通信を検査できる
    負荷分散
    • 複数のサーバへ振り分ける
    • 可用性を高める
    キャッシュ
    • 静的コンテンツをプロキシが応答する
    • サーバの負荷を下げる

  • HAProxy等

RBI
（Remote Browser Isolation）
  • Webブラウザを利用者の端末ではなく隔離環境で実行する
  • 端末には画面のみを転送する
  • Web経由の脅威を遮断する仕組み
  • Webサイトのスクリプトやコンテンツが端末上で実行されないため、以下の被害を抑えられる
    • ドライブバイダウンロード
    • ゼロデイ攻撃
    • フィッシングサイト閲覧による被害
  • 仕組み
    1. 利用者がURLにアクセスすると、クラウド上等の隔離環境のブラウザがそのサイトを読み込む
    2. Webコンテンツ(スクリプト等)は隔離環境側で実行される
    3. 端末には画面の映像や無害化した描画データの描画結果のみが送られる
    4. 端末でのキーボード・マウス操作は隔離環境へ送り返される
  • 動作：「許可するが隔離して閲覧させる」ことができる
  • 守る対象：クライアント(ブラウザ)
  • 未分類サイトやリスクの高いサイトのみRBI経由に振り分ける運用が多い(プロキシ/SWGと連携)
  • コピー・貼り付け、ファイルのダウンロード、印刷等はポリシーで制御できる
  • 課題
    • 操作の遅延
    • 導入コスト
    • 一部サイトの表示互換性
  • ブラウザだけを隔離する方式(VDIとの違いは「エンドポイント防御」のVDIを参照)

  • 検知手法の違いにより下記の方式に分けられる(組み合わせて使われる)

└ パターンマッチング法
（シグネチャ法）
  • 既知のマルウェアの特徴的なコードパターン(シグネチャ)をデータベース化する
  • 検査対象と照合して検知する(ブラックリスト方式)
  • 既知のマルウェアには有効
  • 未知のマルウェア(ゼロデイ攻撃等)には対応できない
  • パターンファイルを常に最新に保つ必要がある
 —
└ ヒューリスティック法
  • マルウェアに共通する特徴的なコード構造・命令列・動作を経験則(ルール)に基づいて評価する
  • 疑わしさの度合いで悪意の有無を判定する
    • シグネチャ(パターンファイル)に依存しない
    • 未知のマルウェアや既存マルウェアの亜種にも対応可能
    • 正常なプログラムを誤って不正と判定する「フォールスポジティブ」が起こりやすい
      用語特徴利用
      フォールスポジティブ
      （誤検知・過検知）
      • 正常な通信・行為を誤って不正と判定してしまうこと
      • 検知を厳しくすると増える(検知漏れとトレードオフ)
      • 検知システムの判定誤りの評価に使う
      • 以下を招く
        • 業務への影響(正常な通信の遮断)
        • アラート対応による運用負荷の増大
      フォールスネガティブ
      （検知漏れ）
      • 実際には不正な通信・行為であるにもかかわらず正常と判定して見逃してしまうこと
      • 検知を緩くすると増える(誤検知とトレードオフ)
      • 検知システムの判定誤りの評価に使う
      • 被害の直接的な原因となりうる
    • 検査方法により「静的ヒューリスティック」と「動的ヒューリスティック」に大別される
      項目静的ヒューリスティック動的ヒューリスティック
      実行の有無実行しない(コードそのものを解析する)実行する(エミュレータ等の仮想環境で動作させる)
      検査内容
      • 逆アセンブル等で命令列・API呼び出し・文字列を調べる
      • マルウェア特有のコードパターンがないかを評価する
      • 実行時の振る舞い(ファイル操作・レジストリ変更・不審な通信など)を評価する
      利点
      • 実際に実行しないため安全
      • 検査も高速
      		難読化されたコードでも、実行時に現れる挙動から検知できる
      欠点
      • 難読化・パッキング・暗号化されたコードは解析しにくい
      • 検知を回避されやすい
      • 実行のため処理に時間がかかる
      • 仮想環境を検知して悪意ある動作を行わないマルウェアには、検知を回避されることがある
  • 動的ヒューリスティックはビヘイビア法(振る舞い検知)に近い考え方

└ ビヘイビア法（振る舞い検知）

  • 挙動(不審なファイル操作・通信等)を監視する
  • 悪意の有無を判定する
  • 未知のマルウェアにも対応可能

└ コンペア法
  • 検査対象ファイルを、あらかじめ保管しておいた原本(感染前のクリーンな状態のファイル)と比較する
  • 差異の有無から感染を判定する
  • 原本を安全に保管・管理する必要がある
  • 正規の更新による変更との区別も必要になる
 —
└ チェックサム法
（インテグリティチェック法）
  • ファイルのハッシュ値(チェックサム)をあらかじめ算出・保管しておく
  • 定期的に再計算した値と比較する
  • 改ざんや感染の有無を検知する
  • 原本全体を保管するコンペア法に比べ、保管するデータが小さくて済む
  • ハッシュ値自体を攻撃者に書き換えられないよう安全な場所に保管する必要がある

VDI
（Virtual Desktop Infrastructure）
  • サーバ上の仮想マシンにデスクトップ環境を構築する
  • 利用者の端末からは画面転送プロトコルで操作する仕組み(仮想デスクトップ)
  • アプリケーションやデータは端末ではなくサーバ側にある
  • 端末とはキーボード・マウス操作と画面情報のみをやり取りする
  • 主な効果
    観点内容
    情報漏えい対策
    • 端末にデータが残らない
    • 紛失・盗難時の漏えいリスクを下げられる
    • コピー・貼り付けやファイルの持ち出しもポリシーで制御できる
    マルウェア対策
    • 端末が感染しても業務データのあるサーバ側へ影響が及びにくい
    • 終了時にクリーンな状態へ戻す「使い捨て」の運用もできる
    一元管理OS・アプリケーション・パッチをサーバ側で一括管理できる
    インターネット分離
    • インターネット接続用のデスクトップを隔離された環境(VDI)で動かす
    • 手元の端末には画面だけを転送する
    • プロキシ経由のWeb閲覧を隔離環境で行う形になる
  • デスクトップ全体を隔離するのがVDI
  • 設置位置：データセンター・クラウド上の仮想デスクトップ
  • 守る対象：端末とデータ(デスクトップ全体)
  • RBIとの違いは「Web・メール防御」のRBIを参照
  • 課題
    • サーバ・ネットワークの導入・運用コスト
    • 画面転送による操作の遅延
  • 基盤となる仮想化サーバ
    用語特徴利用
    仮想化サーバ
    • 1台の物理サーバ上に複数の仮想マシンを構築する技術

      • ハイパーバイザの脆弱性
      • 設定不備
    • ハニーポットやサンドボックスの実行基盤
    • VDIの基盤
    • 検証環境の迅速な構築・破棄

  • OS・ソフトウェアの脆弱性を修正するパッチ(更新プログラム)の適用状況を把握しながら、計画的に配布・適用する運用
  • 既知の脆弱性を放置した端末・サーバが攻撃の入口になりやすい
  • 適用の遅れが被害に直結する
  • 手順
    1. 脆弱性情報の収集(ベンダの公開情報、CVE等)
    2. 自組織の資産への該当確認
    3. 緊急度の評価による優先順位付け(悪用の有無、影響度、CVSS等)
    4. 検証環境での動作確認(業務アプリケーションへの影響確認)
    5. 配布・適用(WSUSやIT資産管理ツール等による一括配布)
    6. 適用状況の確認
    7. 未適用端末のフォロー(検疫ネットワークとの連携)
  • すぐに適用できない場合は暫定対策(緩和策)で被害を抑える

    数字内容
    3データを3つ持つ(原本+バックアップ2つ)
