ネットワーク防御

サービス 概要 種類 説明 製品例
ファイアウォール
  • 基本的な防御機構
  • ネットワークの境界でパケットの送受信を
    制御する
  • 不正な通信を遮断する
  • あらかじめ定めたルール(許可/拒否)に
    基づいて通信を制御する
  • ルールの考え方(「共通の考え方・
    基盤技術」を参照)
    方式 説明
    ブラックリスト方式 原則許可して一部を拒否する
    ホワイトリスト方式 原則拒否して一部のみ許可する
パケットフィルタリング型
  • 最も基本的な方式
    • 送信元/宛先IPアドレス
    • ポート番号
    • プロトコル
      • 等のパケットのヘッダ情報のみで
      ルールベースの許可・拒否を判定する
  • OSI参照モデルの
    • 第3層(ネットワーク層)
    • 第4層(トランスポート層)
    で動作する
  • 高速
  • パケットの中身(ペイロード)は検査しない
  • 通信ごとの状態は見ない
  • 戻りパケット用のルールをあらかじめ固定的に
    開けておく必要がある
 -
ダイナミックパケットフィルタリング型
  • 通信の往路(要求)を監視する
  • 通信状況に応じてフィルタリングルールを
    自動生成する
    • 戻りパケットのみを動的に許可する等
  • 通信が終了したらそのルールを削除する
  • ポートを開けたままにするリスクを減らせる
 -
ステートフルパケットフィルタリング型
ステートフルインスペクションFW
  • セッション(コネクション)の状態を
    管理・追跡する
  • 同一セッションに属する通信のみを許可する
  • なりすましや不正な戻りパケットを排除する
  • 通信の開始から終了までの状態をテーブルで
    管理する
  • TCPの接続手順等に沿わない通信を遮断する
 -
アプリケーションゲートウェイ型
プロキシ型FW
  • アプリケーション層
    (OSI第7層)の内容まで解析する
  • 通信を代理(プロキシ)する
  • 内部と外部の通信を直接つながない
  • クライアント側とサーバ側で別々のセッションを
    張って中継する
  • 厳密な制御ができる
  • 処理負荷が高い
  • プロトコルごとに対応するプロキシが必要
  • 検査精度が高い
  • プロキシの考え方は
    「Web・メール防御」のプロキシサーバを参照
 -
UTM
統合脅威管理
    • ファイアウォール
    • IDS/IPS
    • アンチウイルス
    • アンチスパム
    • URLフィルタリング
    等の複数のセキュリティ機能を1台に
    統合した製品
-
  • ネットワークの出入口(ゲートウェイ)に
    設置する
  • 一括で防御する
  • メリットとデメリット
    区分 内容
    メリット
    • 運用・管理の一元化ができる
    • コスト削減ができる
    デメリット
    • 1台に集中するため障害時の影響が大きい
      • 単一障害点
    • 全機能を有効にすると処理性能が低下しやすい
-
IDS / IPS
不正侵入検知システム /
不正侵入防止システム
  • IDS
    • ネットワークやホスト上の不正な兆候を検知する
    • 管理者に通知する
  • IPSは検知に加えて
    • 不正な通信をリアルタイムに遮断する
    を行う
IDS
  • ネットワークやホスト上の不正な兆候を検知する
  • 管理者に通知する
  • 通信の遮断はしない
  • 監視対象により
    • ネットワーク型の「NIDS」
    • ホスト型の「HIDS」
      (「エンドポイント防御」を参照)
    に分けられる
Snort
NIDS
ネットワーク型IDS
  • ネットワーク上を流れるパケットを監視する
  • ネットワークセグメント全体に
    対する不正アクセスの兆候を検知する
  • 1台のセンサで複数のホストを監視できる
  • 暗号化された通信(HTTPS等)の中身は
    検査できない
 -
IPS
  • IDSの機能に加えて
    • 検知した不正な通信をリアルタイムに
      遮断する機能
    を持つ
  • 設置方法(動作モード)によって
    遮断できるかどうかが変わる(下記の2つ)
 Snort
IPSインラインモード
  • 通信経路上に直接設置する
  • 通過するすべての通信を検査した上で転送する
  • 不正な通信をリアルタイムに遮断できる
  • 通信経路上にあるため
    • IPS自体の障害
    • 性能不足
    が通信全体に影響する(単一障害点)
-
IPSプロミスキャスモード
パッシブモード
  • スイッチのミラーポート(SPAN)や
    タップ等から通信のコピーを受け取って監視する
  • 通信経路上には存在しない
  • 不正な通信そのものを遮断することはできない
  • 検知(IDS的な用途)にとどまる
  • TCPリセットの送信等で接続の切断を
    試みる製品もある
  • 確実な遮断とはいえない
 -
検知方式
IDS・IPS共通
方式 判定の基準 長所 短所 誤検知した場合の影響
シグネチャ型
(ミスユース検知)
  • 既知の攻撃パターンと照合する
  • 一致したものを不正と判定する
    (ブラックリスト的)
 既知の攻撃には確実 未知の攻撃には対応できない
  • IDS・IPSプロミスキャスモード: 通知が
    増えるだけで通信は止まらない
  • IPSインラインモード
    • 正常な通信まで遮断される
    • 業務への影響が大きい
アノマリ型
(異常検知)
  • 正常時の状態を基準とする
  • そこから逸脱したものを不正と判定する
    (ホワイトリスト的)
 未知の攻撃にも対応できる可能性がある 誤検知が起こりやすい
  • アノマリ型は誤検知が起こりやすいため基準の
    調整・学習段階は
    • 通信が止まらないプロミスキャスモード
      (通知のみ)
    で運用するのに向く
-
NDR
Network Detection and Response
  • ネットワークトラフィックを分析する
  • 異常な通信パターンや侵害の兆候を検知する
  • 対応を支援する仕組み
 -
    • EDRを導入できない機器の監視
      • IoT・OT機器
      • 未管理の端末等
    • 侵入後の内部での横展開
      (ラテラルムーブメント)の検知
    に有効
-
検疫ネットワーク
検疫ネットワークシステム
  • 社内ネットワークへの接続前に
    端末のセキュリティ状態を
    検査する専用の隔離ネットワーク
    • パターンファイルの更新状況
    • パッチ適用状況等
 -
  • 基準を満たさない端末は本番ネットワークへの
    接続を許可しない
    1. 端末が接続しようとするとまず検疫用の
      隔離ネットワークに接続させる
    2. OSのパッチやウイルス対策ソフトの
      パターンファイル等の状態を検査する
    3. 基準を満たさない端末は隔離環境で修復
      (パッチ適用・パターンファイル更新等)する
    4. 基準を満たしたことを
      確認してから本番ネットワークへの接続を
      許可する
 -
ZTNA
ゼロトラストネットワークアクセス
  • 「何も信頼しない」ことを前提とする
  • 通信のたびにアクセス主体
    (ユーザ・デバイス)を検証・認可する仕組み
 -
方式 接続範囲
従来のVPN 接続後に社内ネットワーク全体へ
アクセスできてしまいがち
ZTNA 許可されたアプリケーションにのみ接続させる
-
DDoS対策 大量の通信によるサービス停止攻撃に
対する耐性を高める		 DDoS対策サービス
スクラビングサービス
  • 大量トラフィックを専用設備
    (スクラビングセンタ)で吸収・選別する
  • 正常な通信のみをオリジンサーバへ転送する
    • DNSの切り替え
    • BGP経路の広告
    により通信をスクラビングセンタへ迂回させる
-
CDN
コンテンツデリバリネットワーク
  • コンテンツを世界各地のエッジサーバに分散配置
    (キャッシュ)する
  • 利用者に近いサーバから配信する
  • 負荷分散やDDoS攻撃に対する耐性を高められる
  • エッジサーバがリバースプロキシとして応答する
  • オリジンサーバを直接公開せずに済む
 -
DNSSEC
  • DNS応答に電子署名を付与する
  • DNSキャッシュポイズニング等の改ざんを
    検知可能にする仕組み
 -
  • 権威DNSサーバが署名する
  • キャッシュDNSサーバ(フルサービスリゾルバ)が
    検証する
  • 応答の真正性・完全性を確認できる
  • 通信内容の暗号化(秘匿)は行わない
 -

Web・メール防御

サービス 概要 種類 説明 製品例
WAF / WAAP
Web Application Firewall
Web Application and API Protection
  • Webアプリケーション(およびAPI)への攻撃を
    検知・遮断する
  • 通常のFWやIPSでは見分けにくい
    「正規のHTTP通信に見える攻撃」が対象
    • SQLインジェクション
    • XSS等
 WAF
  • HTTP/HTTPS通信の内容を検査する
  • Webアプリケーション層への攻撃を
    検知・遮断する専用のファイアウォール
  • HTTPS通信は復号(TLS終端)した上で検査する
  • 検知のモデルには以下の2つがある
ネガティブセキュリティモデル 既知の攻撃パターンを遮断する
(ブラックリスト的)
ポジティブセキュリティモデル 正規のリクエストの形式のみを許可する
(ホワイトリスト的)
-
WAAP
  • WAFの機能に加えて
    • API保護
      • APIの可視化
      • 不正なAPI呼び出しの遮断
    • ボット対策(不正な自動化アクセスの
      識別・遮断)
    • アプリケーション層(L7)のDDoS対策
    の機能を統合したサービス
-
CSP
Content Security Policy
  • 実行を許可するスクリプトの読み込み元等を
    指定する
  • XSS等の被害を
    軽減するHTTPヘッダベースの仕組み
 -
  • Webサーバが
    Content-Security-Policyレスポンスヘッダで
    ポリシーを通知する
  • ブラウザが許可されていないリソースの読み込み
    ・実行を拒否する
  • 読み込みを許可する配信元を限定する
  • ホワイトリスト方式の一種
 -
プロキシサーバ
  • クライアントとサーバの間に立つ
  • 通信を代理中継する中継サーバ
  • 設置位置によって守る対象が変わる
    • クライアント側ならクライアント
    • サーバ側ならサーバ
  • 代理中継の考え方は
    アプリケーションゲートウェイ型FWにも
    使われる(「ネットワーク防御」の
    ファイアウォールを参照)
 フォワードプロキシ
  • クライアントの代理として外部のサーバと
    通信する
  • クライアント側(組織内)と
    インターネットの間に設置する
  • 悪意あるサーバ(マルウェア配布サイト・
    フィッシングサイト・C2サーバ等)から
    クライアントを守る
クライアントの隠蔽
  • 外部サーバにはプロキシのIPアドレスしか
    見えない
  • クライアントに直接接続されない
アクセス制御
    • URLフィルタリング
    • 認証
    により危険・不要なサイトへのアクセスを
    制限する
コンテンツ検査
    • ダウンロードされるファイルの
      マルウェアスキャン
    • TLS通信の復号検査(SSLインスペクション)
    を行う
ログ取得
  • 誰がどこにアクセスしたかを記録する
  • インシデント調査や監査に利用する
キャッシュ
  • 同じコンテンツの再取得を省く
  • 帯域を節約する
  • プロキシを迂回する通信は検査できない
  • FWで直接の外部通信を禁止して経由を強制する
  • クラウド型や高機能化したものはSWG
    (Secure Web Gateway)とも呼ばれる
 Squid
リバースプロキシ
  • サーバの代理として外部クライアントからの
    リクエストを受け付ける
  • 内部のWebサーバ等へ中継する
  • Webサーバ等の前段(DMZや
    クラウドの入口)に設置する
  • 悪意あるクライアント
    (攻撃者)からサーバを守る
  • フォワードプロキシとは通信の向きが逆
  • 代理する相手・守る対象が「サーバ側」になる
サーバの隠蔽
  • 内部サーバの
    • IPアドレス
    • 構成
    • ソフトウェアのバージョン等
    が外部から見えず直接攻撃されない
攻撃の遮断
  • WAF機能と組み合わせる
  • 不正なリクエストを内部サーバへ到達させない
TLS終端
  • 暗号化・復号をプロキシが代行する
  • サーバの負荷を軽減する
  • 復号後の通信を検査できる
負荷分散
  • 複数のサーバへ振り分ける
  • 可用性を高める
キャッシュ
  • 静的コンテンツをプロキシが応答する
  • サーバの負荷を下げる
  • CDNのエッジサーバはリバースプロキシを
    世界中に分散配置した仕組みといえる
  • Nginx
  • HAProxy等
メールプロキシ
SMTPプロキシ
  • プロキシの考え方をメール(SMTP)
    通信に応用したもの
  • メールサーバの前段に設置する
    • 送受信されるメールの内容検査・フィルタリング
    • 送信元の正当性確認
    を代理で行う
受信方向(リバースプロキシ的)
  • 外部から届くメールを内部メールサーバの
    代わりに受け取る
  • スパム・ウイルス・フィッシングメールを
    検査・排除してから転送する
送信方向(フォワードプロキシ的)
  • 社内から外部へ送るメールを検査する
  • 情報漏えい(誤送信・不正な持ち出し)や
    ウイルスの拡散を防ぐ

URLフィルタリング
Webフィルタリング
  • 危険・不要なWebサイトへのアクセスを
    • URLのレピュテーション情報
    • カテゴリ分類
    に基づいて制限する仕組み
-
  • 制限の対象は業務上不要・危険なカテゴリの
    Webサイト
    • 悪意あるサイト
    • 危険なダウンロード元
    • フィッシングサイト等
  • フォワードプロキシ(SWG)や
    UTM等の機能として実装されることが多い
  • ブラックリスト方式・
    ホワイトリスト方式のどちらでも運用できる
    (「共通の考え方・基盤技術」を参照)
 -
RBI
Remote Browser Isolation
  • Webブラウザを利用者の端末ではなく隔離環境で
    実行する
  • 端末には画面のみを転送する
  • Web経由の脅威を遮断する仕組み
 -
  • Webサイトのスクリプトやコンテンツが端末上で
    実行されない    ため
    • ドライブバイダウンロード
    • ゼロデイ攻撃
    • フィッシングサイト閲覧による被害
    の被害を抑えられる
    1. 利用者がURLにアクセスすると
      クラウド上等の隔離環境のブラウザがその
      サイトを読み込む
    2. Webコンテンツ(スクリプト等)は隔離環境側で
      実行される
    3. 端末には
      • 画面の映像
      • 無害化した描画データ
      の描画結果のみが送られる
    4. 端末でのキーボード・マウス操作は隔離環境へ
      送り返される
  • URLフィルタリングとの違い
    方式 動作
    URLフィルタリング 「許可/ブロック」の二択
    RBI 「許可するが隔離して閲覧させる」ことができる
  • 未分類サイトやリスクの
    高いサイトのみRBI経由に振り分ける運用が多い
    (プロキシ/SWGと連携)
    • コピー・貼り付け
    • ファイルのダウンロード
    • 印刷等
    はポリシーで制御できる
  • 課題
    • 操作の遅延
    • 導入コスト
    • 一部サイトの表示互換性
  • デスクトップ全体を隔離するVDI
    (「エンドポイント防御」を参照)に
    対しブラウザだけを隔離する方式

迷惑メール対策

  • 拒否・隔離する方式の総称
  • 単独ではなく複数を組み合わせて使われる
 ブラックリスト方式

  • 既知の迷惑メール送信元

  • 該当するメールを拒否・隔離する
  • DNSBL(RBL)として公開されているリストを

ベイジアンフィルタ
  • 過去の迷惑メール・正常メールの単語出現傾向を

  • 確率的に迷惑メールかどうかを判定する
    (ベイズの定理を利用)
  • 未知の迷惑メールにも対応できる
  • 利用者ごとに学習させることで精度が向上する
  • 学習データが少ないうちは精度が低い
  • 誤判定も起こりうる
 -
グレーリスティング
  • 未知の送信元からの初回メールを一時的に
    拒否し再送してくるかどうかで
    正規のメールサーバかを判別する
    1. 未知の送信元(IPアドレス・送信者・宛先の
      組)からの初回の配送をSMTPの一時エラー
      (4xx)で拒否する
    2. 正規のメールサーバには
      再送の仕組みがあるため一定時間後に
      再送してくる
    3. 再送を確認できた送信元を許可リストに
      登録し以降のメールを受け付ける
  • 再送機能を持たない迷惑メール送信プログラムを
    排除できる
  • 初回の配送が遅れる
 -
送信ドメイン認証
SPF / DKIM / DMARC
  • 送信元ドメインのなりすましを検知する
  • 正規の送信元からのメールであることを検証する
  • なりすましメール(フィッシング等)
    対策の代表技術
  • 受信側が検証して結果に応じた処理を行う
 SPF
Sender Policy Framework 		送信元ドメインのDNSに
登録された正規の送信サーバのIPアドレスと
実際の送信元IPアドレスを照合する		 -
DKIM
DomainKeys Identified Mail
  • 送信側がメールに電子署名を付与する
  • 受信側がDNSで公開された公開鍵で署名を
    検証する(メールの改ざんも検知できる)
 -
DMARC
Domain-based Message Authentication,
Reporting and Conformance
  • SPF/DKIMの検証結果と
    Fromヘッダのドメインとの整合性に基づく
  • 認証失敗時の扱いを送信側が宣言する
    • 何もしない
    • 隔離
    • 拒否
  • 認証結果のレポートも受け取れる

エンドポイント防御

サービス 概要 種類 説明 製品例
アンチウイルスソフト
  • 既知のマルウェアのパターン(シグネチャ)や
    挙動を検知・駆除するソフトウェア
  • 検知手法の違いにより右の方式に分けられる
    (組み合わせて使われる)
 パターンマッチング法
シグネチャ法
  • 既知のマルウェアの特徴的なコードパターン
    (シグネチャ)をデータベース化する
  • 検査対象と照合して検知する
  • 既知のマルウェアには有効
  • 未知のマルウェア(ゼロデイ攻撃等)には
    対応できない
  • パターンファイルを常に最新に保つ必要がある
 -
ヒューリスティック法
  • マルウェアに共通する特徴的なコード構造・
    命令列・動作を経験則(ルール)に
    基づいて評価する
  • 疑わしさの度合いで悪意の有無を判定する
    • シグネチャ(パターンファイル)に依存しない
    • 未知のマルウェアや既存マルウェアの亜種にも
      対応可能
    • 正常なプログラムを誤って不正と判定する
      「フォールスポジティブ」が起こりやすい
    • 検査方法により「静的ヒューリスティック」と
      「動的ヒューリスティック」に
      大別される(下表)
項目 静的ヒューリスティック 動的ヒューリスティック
実行の有無 実行しない(コードそのものを解析する) 実行する(エミュレータ等の仮想環境で
動作させる)
検査内容
  • 逆アセンブル等で命令列・API呼び出し・
    文字列を調べる
  • マルウェア特有のコードパターンがないかを
    評価する
  • 実行時の振る舞いを評価する
    • ファイル操作
    • レジストリ変更
    • 不審な通信など
利点
  • 実際に実行しないため安全
  • 検査も高速
 難読化されたコードでも実行時に
現れる挙動から検知できる
欠点
  • 難読化・パッキング・暗号化されたコードは
    解析しにくい
  • 検知を回避されやすい
  • 実行のため処理に時間がかかる
  • 仮想環境を検知して悪意ある動作を
    行わないマルウェアには検知を
    回避されることがある
  • 動的ヒューリスティックはビヘイビア法
    (振る舞い検知)に近い考え方
 -
ビヘイビア法
振る舞い検知
  • プログラムを
    • 実際の環境
    • 模擬環境(サンドボックス)
    のいずれかで動作させる
  • 挙動(不審なファイル操作・通信等)を監視する
  • 悪意の有無を判定する
  • 未知のマルウェアにも対応可能
 -
コンペア法
  • 検査対象ファイルをあらかじめ保管しておいた
    原本(感染前のクリーンな状態のファイル)と
    比較する
  • 差異の有無から感染を判定する
  • 原本を安全に保管・管理する必要がある
  • 正規の更新による変更との区別も必要になる
 -
チェックサム法
インテグリティチェック法
  • ファイルのハッシュ値
    (チェックサム)をあらかじめ算出・
    保管しておく
  • 定期的に再計算した値と比較する
  • 改ざんや感染の有無を検知する
  • 原本全体を保管するコンペア法に
    比べ保管するデータが小さくて済む
  • ハッシュ値自体を攻撃者に
    書き換えられないよう安全な場所に
    保管する必要がある
 -
EDR
Endpoint Detection and Response
  • エンドポイント(PC・サーバ)上の挙動を監視し
    • 侵害の検知
    • 調査
    • 封じ込め(端末のネットワーク隔離等)
    を行う仕組み
-
  • プロセス・ファイル操作・通信等の挙動を
    継続的に監視・記録する
  • アンチウイルス等の入口対策をすり抜けた
    脅威への対応(侵入後の対策)に有効
 -
HIDS
ホスト型IDS
  • サーバやPC等個々のホスト上にエージェントを
    常駐させる
    • ログの改ざん
    • ファイルの変更
    • プロセスの異常等
    を監視する方式
-
  • ホスト内部の変化を直接監視できる
  • 監視対象ごとにエージェントの導入・管理が必要
 -
デバイス制御
USBデバイス制御 		USBメモリ等の外部記憶媒体や周辺機器の接続・
利用を端末上のソフトウェア(エージェント)で
制御する仕組み		 -
  • 許可した機器(登録済みのUSBメモリ等)のみ
    利用を認める(ホワイトリスト方式)
  • 書き込みのみ禁止(読み取り専用)にする等
    操作単位で制限する
  • 機器の利用ログを記録する
  • 情報の持ち出しやマルウェアの侵入を防止する
  • 物理的にポートを塞ぐ方法は
    「物理的対策」のUSBポートロックを参照
 -
VDI
Virtual Desktop Infrastructure
  • サーバ上の仮想マシンにデスクトップ環境を
    構築する
  • 利用者の端末からは画面転送プロトコルで
    操作する仕組み(仮想デスクトップ)
 -
  • アプリケーションやデータは
    端末ではなくサーバ側にある
  • 端末とはキーボード・マウス操作と
    画面情報のみをやり取りする
情報漏えい対策
  • 端末にデータが残らない
  • 紛失・盗難時の漏えいリスクを下げられる
  • コピー・貼り付けやファイルの持ち出しも
    ポリシーで制御できる
マルウェア対策
  • 端末が感染しても業務データのあるサーバ側へ
    影響が及びにくい
  • 終了時にクリーンな状態へ戻す
    「使い捨て」の運用もできる
一元管理 OS・アプリケーション・パッチをサーバ側で
一括管理できる
インターネット分離
  • インターネット接続用のデスクトップを
    隔離された環境(VDI)で動かす
  • 手元の端末には画面だけを転送する
  • プロキシ経由のWeb閲覧を隔離環境で
    行う形になる
  • デスクトップ全体を隔離するのがVDI
  • ブラウザだけを隔離するのがRBI
    (「Web・メール防御」を参照)
  • 課題
    • サーバ・ネットワークの導入・運用コスト
    • 画面転送による操作の遅延
 -
資産管理
IT資産管理 / MDM
  • 組織が保有するPC・サーバ・スマートフォン・
    ソフトウェア等のIT資産を把握する
  • 構成や状態を管理する取り組み
  • 把握できていない資産は守れない
  • 他のあらゆる対策の前提となる
 IT資産管理ツール
    • 端末のハードウェア構成
    • OS・ソフトウェアのバージョン
    • ライセンス情報
    等の情報をエージェントで自動収集し台帳
    (インベントリ)として管理する
    • パッチ未適用の端末の検出
    • 禁止・不要なソフトウェアのインストールの検出
    • 台帳に載っていない未管理端末
      (シャドーIT)の発見
    • 操作ログの取得
    • ソフトウェアの配布・インストールの制限
 -
MDM
Mobile Device Management
  • スマートフォン・タブレット等のモバイル端末を
    遠隔から一元管理する
    • パスコードや端末の暗号化の強制
    • 紛失・盗難時のリモートロックやデータ消去
      (ワイプ)
    • 利用できるアプリの制限・配布
 -
パッチ管理
  • OS・ソフトウェアの脆弱性を修正するパッチ
    (更新プログラム)を適用状況を
    把握しながら計画的に配布・適用する運用
  • 既知の脆弱性を放置した端末・サーバが
    攻撃の入口になりやすい
  • 適用の遅れが被害に直結する
 -
  1. 脆弱性情報の収集
    • ベンダの公開情報
    • CVE等
  2. 自組織の資産への該当確認
  3. 緊急度の評価による優先順位付け
    • 悪用の有無
    • 影響度
    • CVSS等
  4. 検証環境での動作確認
    (業務アプリケーションへの影響確認)
  5. 配布・適用(WSUSやIT資産管理ツール等による
    一括配布)
  6. 適用状況の確認
  7. 未適用端末のフォロー
    (検疫ネットワークとの連携)
  • すぐに適用できない場合は暫定対策(緩和策)で
    被害を抑える
    • IPS・WAFによる仮想パッチ
    • 該当機能の無効化等

データ保護

サービス 概要 種類 説明 製品例
DLP
Data Loss Prevention 		機密情報の外部送信・持ち出しを
検知・防止する仕組み		 -
  • 機密情報のキーワードやデータ形式・ラベル等に
    基づいて検知する
    • メール送信
    • USBメモリへの書き出し
    • クラウドへのアップロード
    等を警告・ブロックする
  • 監視する場所により
    • エンドポイント型
    • ネットワーク型(メール/Web)
    • クラウド型
    等の型がある
-
暗号化
  • データを第三者が読めない形に変換する
  • 盗難・盗聴・漏えいが起きても内容を
    読まれないようにする
  • 「保管中のデータ」と
    「通信中のデータ」の両方を対象とする
  • あわせて暗号鍵を管理する
 保管データの暗号化
データ at rest
  • ディスク・ファイル・データベース・
    バックアップ等に保存されたデータを暗号化する
    • 端末の紛失・盗難
    • サーバからのデータ持ち出し
    による情報漏えいに備える
    • ディスク全体を暗号化
    • ファイル単位
    • データベース単位(列・表領域)
    の暗号化がある
BitLocker等
通信の暗号化
データ in transit
  • ネットワーク上を流れるデータを暗号化する
  • 盗聴・改ざんを防ぐ
Web TLS(HTTPS)
リモート接続
  • VPN(IPsec・TLS-VPN)
  • SSH
メール STARTTLS等によるSMTP通信の暗号化
  • 暗号化された通信の中身はFWやIDS/IPSでは
    検査できない
  • WAF・プロキシ等で復号
    (TLS終端)して検査する構成がとられる
 -
鍵管理
  • 暗号鍵の生成・保管・更新(ローテーション)
    ・失効・廃棄を管理する
  • 鍵が漏えいすると暗号化の効果が失われる
  • データとは別の場所で厳重に保管する
    • 鍵管理サービス(KMS)
    • 耐タンパ性を持つ専用装置(HSM)
    が使われる
-
バックアップ
  • データやシステムの複製を別の場所に保管する
  • 障害・誤操作・ランサムウェア等による
    被害からの復旧を可能にする
  • 取得するだけでなく確実に復元できることまで
    確認して初めて有効な対策となる
 3-2-1ルール
  • バックアップ設計の基本的な考え方
3 データを3つ持つ(原本+バックアップ2つ)
2 2種類以上の異なる媒体に保存する
(例: ディスクとテープ・クラウド)
1 1つは遠隔地(オフサイト・クラウド)に保管する
  • ランサムウェア対策としてさらに
    • 1つはオフライン/変更不可とする
    • 復元テストでエラーが0であることを確認する
    を加えた「3-2-1-1-0」という考え方もある
-
オフライン・イミュータブル保管
  • バックアップ自体の暗号化・削除を
    • ネットワークから切り離した保管(オフライン)
    • 書き換え・削除ができない設定
      (イミュータブル)
    により防ぐ
  • ネットワークに常時接続したバックアップは
  • ランサムウェアに原本と一緒に
    暗号化・削除されるおそれがある
 -
復元テスト
  • 定期的に実際に復元できることを確認する
  • 指標 内容
    目標復旧時点(RPO) どの時点まで戻せるか
    目標復旧時間(RTO) いつまでに復旧するか
    をあらかじめ定めバックアップの頻度・
    方式を決める

クラウドセキュリティ

サービス 概要 種類 説明 製品例
CASB
Cloud Access Security Broker
  • クラウドサービスの利用状況を可視化する
  • セキュリティポリシーを適用・統制する仕組み
 -
  • 利用者とクラウドサービスの間に位置する
    • 許可されていないクラウドサービスの利用
      (シャドーIT)の検出
    • 機密データのアップロード制限
    • 不審な操作の検知等
    を行う
  • 自組織が構築したクラウド環境の設定不備を
    検出するCSPMとは対象が異なる(同じ
    「クラウドセキュリティ」のCSPMを参照)
 -
CSPM
Cloud Security Posture Management
  • IaaS/PaaS等のクラウド環境の設定を継続的に
    監視する
  • 設定不備(ミスコンフィグレーション)を
    検出・是正する仕組み
 -
  • クラウドでは設定ミスが情報漏えいに直結する
  • 設定状態を自動でチェックする
  • クラウド事業者との責任共有モデルにおいて
    利用者側が責任を負う設定部分が対象となる
    • インターネットに公開された
      オブジェクトストレージの検出
      • 過剰な権限
      • 不要な公開ポート
      • 暗号化の無効化
      • ログ未取得
      等の検出
    • CISベンチマーク等の基準や
      コンプライアンス要件との照合
    • リスクの優先順位付け
    • 是正手順の提示
    • 自動修復
  • CASBとCSPMの違い
    製品 対象
    CASB 「利用者によるクラウドサービスの使い方」を
    統制する
    CSPM 「自組織が構築したクラウド環境の設定状態」を
    監視する
  • ワークロード保護(CWPP)等と統合した
    「CNAPP」として提供されることも多い

検知・分析基盤

サービス 概要 種類 説明 製品例
SIEM / SOAR / XDR
  • ログや検知情報を集約・分析して脅威を早期に
    発見する
  • 対応を効率化する仕組み
  • 役割
    製品 役割
    SIEM 「見つける」
    SOAR 「自動で対応する」
    XDR 「複数レイヤの情報を束ねる」
SIEM
Security Information and Event Management
  • 各種機器・システム(FW・サーバ・認証基盤・
    クラウド等)のログを収集・正規化する
  • 相関分析することでインシデントの早期発見を
    支援する
 -
SOAR
Security Orchestration, Automation and Response
  • インシデント対応プロセス(プレイブック)を
    自動化・オーケストレーションする
  • 対応の迅速化を図る
  • SIEM等のアラートを起点に
    • 不審なIPアドレスの遮断
    • 侵害が疑われる端末のネットワーク隔離
    • チケットの起票・担当者への通知
    のような対応を自動で実行する
-
XDR
Extended Detection and Response
    • エンドポイント(EDR)
    • ネットワーク
    • メール
    • クラウド
    • ID等
    の複数のレイヤの情報を統合・相関分析して
    脅威を検知・対応する
  • 個別の製品ごとにバラバラだったアラートを
    関連付ける
  • 攻撃の全体像を把握しやすくする
 -
サンドボックス / ハニーポット
  • 隔離された環境で
    • マルウェアの挙動
    • 攻撃者の手口
    を観察する
  • 本番環境に被害を出さない
  • どちらも仮想化サーバ上に構築されることが多い
 サンドボックス
  • 疑わしいファイルやプログラムを
    本番環境から隔離された仮想環境で実行する
  • その挙動を観察して安全性を検証する
  • アクセスできるリソースや利用できる機能を
    制限している
    • ファイルシステム
    • レジストリ
    • ネットワーク通信等
  • マルウェアが動作しても本番環境に被害が
    及ばない
    • メールの添付ファイル検査
    • Web閲覧
    • エンドポイント
    等の様々な製品に組み込まれる
  • ビヘイビア法(振る舞い検知)の実行環境として
    利用される
  • 仮想環境を検知して動作を隠すマルウェアもある
 -
ハニーポット
  • 攻撃者を誘引するためわざと脆弱に
    見せかけたシステム・機器を設置する
