パスワード認証
(固定式)
 ID(利用者識別子)とパスワード(秘密の文字列)の組み合わせによる、
最も基本的な知識情報ベースの認証方式
sequenceDiagram participant U as 利用者 participant S as サーバ U->>S: 1. IDとパスワードを入力 S->>S: 2. 登録済みの文字列と照合 S-->>U: 3. 一致すれば認証成功
手順内容
1利用者がIDとパスワードを入力する
2サーバが登録済みの文字列と照合する
3一致すれば認証成功とする
  • 追加機器が不要で導入・利用が容易
  • 利用者にとって分かりやすく広く普及
  • 使い回し・単純な文字列は辞書攻撃・リスト型攻撃・パスワードスプレー攻撃に弱い
  • フィッシング・盗聴・漏えいで盗まれると悪用される
  • 利用者の記憶の負担
  • 最も普及している認証方式
  • 単体では強度が低いため、多要素認証の
    1要素として組み合わせて使われることが多い
  • 保存時はソルト付きハッシュ化、運用面では
    アカウントロックアウト等の対策と併用するのが一般的

(Password Authentication
Protocol)
 PPP接続等で使われる、
ID/パスワードを平文のまま送信する最も単純な認証プロトコル
sequenceDiagram participant C as クライアント participant S as サーバ C->>S: 1. IDとパスワードを平文で送信 S->>S: 2. 登録済みの文字列と照合 S-->>C: 3. 一致すれば認証成功

3一致すれば認証成功とする

  • 平文送信のため盗聴で容易にパスワードが漏洩する
  • 接続時の1回のみ認証で、リプレイ攻撃にも弱い

  • CHAP等への移行が推奨される
  • リモートアクセス認証
    (ダイヤルアップ等、現在はほぼ非推奨)
チャレンジレスポンス認証
 パスワード等の秘密情報をネットワーク上に
平文で流さずに認証する方式
チャレンジはサーバが毎回変える乱数(使い捨て)のため、リプレイ攻撃を防げる
  • 検証方式
    サーバが出したチャレンジと共有秘密から計算したハッシュ値が、
    クライアントのレスポンスと一致するか    を確認する
sequenceDiagram participant C as クライアント participant S as サーバ S->>C: 1. チャレンジ(乱数)を送付 C->>C: 2. チャレンジとパスワードからハッシュ値等を計算 C->>S: 2. レスポンスとして返送 S->>S: 3. 同じ計算を行い一致を確認
手順内容
1サーバがランダムな「チャレンジ」(乱数)を送付する
2クライアントはチャレンジとパスワードから
ハッシュ値等を計算し「レスポンス」として返送する
3サーバも同じ計算を行い一致を確認する
  • パスワードを平文でネットワークに流さない
  • 毎回異なる乱数(チャレンジ)によりリプレイ攻撃を防げる
  • サーバ側に共有秘密を(復元可能な形で)保持する必要がある方式が多い
  • 通信を傍受されるとオフラインでの辞書攻撃を受けうる
  • リプレイ攻撃対策になる
  • APOP、CHAP等で利用
CHAP
(Challenge Handshake
Authentication Protocol)
 PPP接続等で使われる
チャレンジレスポンス方式の代表的プロトコル
sequenceDiagram participant C as クライアント participant S as サーバ S->>C: 1. チャレンジを送付(接続開始時) C->>S: 1. レスポンス(ハッシュ値)を返送 S-->>C: 1. 認証結果を通知 S->>C: 2. 接続中も定期的にチャレンジを再送(再認証) C->>S: 2. レスポンスを返送 Note over C,S: 3. パスワードは平文で送らない(PAPとの違い)
手順内容
1接続開始時にチャレンジレスポンス認証を行う
2接続中も定期的に再認証を行う
3PAPと異なりパスワードを平文で送らない
  • パスワードを平文で送らない
  • 接続中の定期的な再認証でセッション乗っ取りを抑える
  • サーバ側が秘密を復元可能な形で保持する必要がある
  • MD5ベースで強度は高くない
  • クライアントのみを認証する(相互認証ではない)
  • リモートアクセス認証
    (ダイヤルアップ、VPN等)
XMLデジタル署名
(XML Signature)
 XML文書(全体・一部の要素・外部リソース)に対するデジタル署名の標準規格
署名情報自体もXML(<Signature>要素)で表現される
形式の違いは「署名と署名対象の位置関係」で決まり、直下の3形式に分かれる
なお1つの<Signature>は複数の<Reference>を持てるため、
1対1・1対多といった数の関係は形式ではなく<Reference>の数で決まる
XMLは意味が同じでも空白・属性順等の表記が変わりうるため、
署名・検証の前に「正規化(C14N : Canonicalization)」を行う
主な構成要素 :
  • <SignedInfo> : 署名対象の情報のまとまり(実際に署名される要素)
  • <Reference> :
    署名対象1件分の参照(URI、Transforms、DigestMethod、DigestValue)
    複数指定可
  • <SignatureValue> : <SignedInfo>に対する署名値
  • <KeyInfo> : 検証用の公開鍵・証明書(省略可)
  • <Object> : エンベロピング署名で対象データを格納する要素
sequenceDiagram participant A as 署名者 participant V as 検証者 A->>A: 1. 署名対象をReferenceのURIで指定 A->>A: 2. 変換(正規化等)後にダイジェストを計算しDigestValueに格納 A->>A: 3. SignedInfoを正規化し秘密鍵で署名してSignatureValueを生成 A->>A: 4. KeyInfoを付与しSignature要素を形式に応じた位置に配置 A->>V: 4. 署名付きXMLを送付 V->>V: 5. DigestValueの再計算とSignatureValueの公開鍵検証を両方行う
手順内容
1署名対象を<Reference>のURIで指定する
2対象に変換(Transform : 正規化等)を適用し、ダイジェストを計算して<DigestValue>に格納する
3<SignedInfo>を正規化し、秘密鍵で署名して<SignatureValue>を生成する
4<KeyInfo>を付与し、<Signature>要素を形式に応じた位置に配置する
5検証時はDigestValueの再計算と、SignatureValueの公開鍵による検証の両方を行う
  • XML文書の全体・一部・外部リソースを署名でき、改ざん検知と署名者の確認ができる
  • W3C勧告の標準で相互運用しやすく、1つの署名で複数対象を扱える
  • 正規化・Transform等の仕様が複雑で、実装ミスが脆弱性に直結する(XML Signature Wrapping、XXE等)
  • 署名と署名対象の位置関係を誤ると検証漏れが起きる
  • デジタル署名・証跡
  • SOAPメッセージ(WS-Security)
  • 電子申請システム等
  • XAdES(XML署名にタイムスタンプ等を加えた長期署名の拡張規格)
  • XML Encryption(XMLの暗号化規格)とは別規格
 └ エンベローピド署名
(Enveloped Signature)
  • 署名が、対象に包まれる(対象の内側に署名を書く)

対象
  • 署名を含む文書全体(URI="")
  • 署名を含む特定の親要素(URI="#id")

署名関係
  • 基本
    1署名 : 1文書(1対1)
  • 署名者が複数
    署名を追加して多対1も可能
    (他の署名を対象に含めるかの設計が必要)

署名場所
  • 対象の内部に書く
    (「属する文書」が対象)
  • 署名自身が対象に含まれてしまうため、
    署名要素を対象から除外する変換(enveloped-signature)が必須

構造イメージ
Invoice ←署名対象
 ├ Amount
 └ Signature ←対象の内側
sequenceDiagram participant A as 署名者 participant D as 対象文書 A->>D: 1. 署名対象(通常は文書全体)をReferenceで指定 A->>D: 2. Transformsにenveloped-signature変換と正規化を指定 A->>A: 3. ダイジェストを計算しSignedInfoに署名 A->>D: 4. Signature要素を対象文書の内部に挿入
手順内容
1署名対象(通常は文書全体 : URI="")を<Reference>で指定する
2Transformsに「enveloped-signature変換」と正規化を指定する
3ダイジェストを計算し、<SignedInfo>に署名する
4<Signature>要素を対象文書の内部に挿入する
  • 署名と文書が1ファイルで完結し、配布・保管が容易
  • 署名自身を対象から除外する変換(enveloped-signature)が必須
  • 署名の挿入により元の文書が変更される
  • XML以外のデータは直接扱えない
  • 1ファイルで署名と文書を完結させたい場合
  • SAMLアサーション・レスポンスの署名
  • 電子申請の署名付きXML文書
 └ エンベロピング署名
(Enveloping Signature)
  • 署名が、対象を包む(署名の内側に対象を書く)

対象
  • <Signature>内の<Object>要素に格納したデータ
  • XML以外のデータ(Base64化したバイナリ等)も対象にできる

署名関係
  • 1署名 : 1つ以上の<Object>
  • Objectを複数入れれば1署名で複数データを署名(1対多)

署名場所
  • 署名が親、対象が子(対象は署名の内部に書く)
  • <Reference>でURI="#id"により内側のObjectを参照
  • 元データを使うには署名要素から取り出す

構造イメージ
Signature ←署名が外側
 └ Object ←対象が内側
   └ 対象データ
sequenceDiagram participant A as 署名者 participant S as Signature要素 A->>S: 1. 署名対象データをObject要素に格納 A->>S: 2. ReferenceでそのObject要素をID参照 A->>A: 3. ダイジェストを計算しSignedInfoに署名
手順内容
1署名対象データを<Signature>内の<Object>要素に格納する
2<Reference>でそのObject要素をID参照(URI="#id")する
3ダイジェストを計算し、<SignedInfo>に署名する
  • バイナリ等XML以外のデータも署名できる
  • 署名と対象が一体で配布できる
  • 元データを使うには署名要素から取り出す必要がある
  • Base64化によりサイズが増える
  • バイナリや任意データを1つのXMLにまとめて署名する用途
 └ デタッチ署名
(Detached Signature)
  • 署名と対象が、互いに包まず別々(署名は対象を参照するだけ)

対象
  • 同一XML文書内の特定要素(URI="#id")
  • 外部ファイル(URI="https://…")
  • 混在(文書の一部だけを対象にできる)

署名関係
  • 1署名で複数の要素・リソースをまとめて署名(1対多)
  • 複数署名者が同じ対象に署名(多対1)
  • 多対多
  • 3形式中最も柔軟

署名場所
  • 対象の外側に書き、対象を参照する
  • 同一文書内の別要素への署名なら、同じXML文書に含めることも可能(対象の兄弟要素などに配置)
  • 対象を改変せずに署名できるが、署名と対象が分離すると検証できない

構造イメージ
Order ←署名対象①(id=o1)
Item ←署名対象②(id=i1)
Signature ←対象の外側から参照
 ├ Reference URI="#o1"
 └ Reference URI="#i1"
sequenceDiagram participant A as 署名者 participant T as 署名対象(要素・外部リソース) participant S as Signature要素 A->>T: 1. 署名対象をReferenceのURI(ID参照または外部URI)で指定 A->>A: 2. ダイジェストを計算しSignedInfoに署名 A->>S: 3. Signature要素を対象の外側(別ファイルまたは同一文書内の別位置)に配置
手順内容
1署名対象の要素・リソースを<Reference>のURI(#idまたは外部URI)で指定する
2ダイジェストを計算し、<SignedInfo>に署名する
3<Signature>要素を対象の外側(別ファイル、または同一文書内の別の位置)に配置する
  • 3形式中で最も柔軟(1対多・多対1・多対多)
  • 元の文書を改変せずに署名でき、文書の一部や外部リソースも対象にできる
  • 署名と対象が分離すると検証できない
  • ID参照方式ではXML Signature Wrapping攻撃に注意が必要
  • 外部URI参照は取得失敗・内容変更の管理が必要
  • 文書の一部の要素だけに署名する用途
  • SOAPメッセージのヘッダ・ボディ等の個別要素の署名(WS-Security)
  • 注意 : ID参照方式では、署名済み要素を別の位置へ移して偽要素を差し込む
    XML Signature Wrapping攻撃に備え、署名された要素そのものを処理に使うこと
タイムスタンプ
(デジタルタイムスタンプ)
 ある時刻にその電子データが「存在していたこと」
「改ざんされていないこと」を証明する技術
デジタル署名だけでは「いつ」署名したかは
証明できないため併用される
sequenceDiagram participant U as 利用者 participant T as 時刻認証局(TSA) U->>T: 1. データのハッシュ値を送付 T->>T: 2. ハッシュ値と時刻情報を結合し署名 T-->>U: 3. タイムスタンプを付与(完全性と存在時刻を証明)
手順内容
1データのハッシュ値を時刻認証局(TSA)に送付する
2TSAがハッシュ値と時刻情報を結合し署名する
3付与されたタイムスタンプにより完全性と存在時刻を証明する
  • 第三者(TSA)がデータの存在時刻と非改ざんを証明できる
  • デジタル署名と併用して長期署名の有効性を保てる
  • TSAへの依存とコストが発生する
  • タイムスタンプ自体にも有効期限(TSA証明書の期限)があり、更新が必要
  • 時刻と完全性の証明のみで、内容の正しさは証明しない
  • デジタル署名・証跡
  • 長期署名(電子契約、電子帳簿保存法対応等)

(コード署名)
 ソフトウェア(実行ファイル、ドライバ、アプリ等)の
作成者・非改ざんを証明する署名

  • モバイルアプリ配布
  • マルウェア対策
トランザクション署名
  • 取引内容(振込先・金額等)そのものを署名対象データに含めて、
    利用者側の署名デバイスで署名(またはMAC/ワンタイムパスワードを生成)し、
    サーバが検証する方式
  • 取引内容が改ざんされると署名が一致せず検証に失敗するため、
    MITB(Man-in-the-Browser)攻撃対策となる
sequenceDiagram participant U as 利用者(PC) participant S as サーバ participant D as 署名デバイス U->>S: 1. ログイン認証を行う U->>S: 2. 取引を依頼(振込先・金額等を入力) S->>D: 3. 受け付けた取引内容を別デバイスに表示 D->>D: 4. 利用者が表示内容を確認し署名を生成 U->>S: 5. 署名を送信 S->>S: 5. 取引内容と署名を照合し一致した場合のみ実行
手順内容
1ログイン認証を行う
2PCから取引を依頼する
(振込先・金額等を入力)
3サーバが受け付けた取引内容を、
PCとは別の署名デバイスに表示する
4利用者が表示内容を確認し、
署名デバイスで署名を生成する
5サーバが、受け付けた取引内容と署名を照合し、
一致した場合のみ実行する
  • 取引内容そのものを署名するため、MITB攻撃による取引内容の改ざんを検知できる
  • 別デバイスの表示で利用者が内容を確認できる
  • 専用デバイス・アプリが必要でコスト・利便性が低下する
  • 利用者が表示内容を確認しないと効果が薄れる
  • デバイスの紛失対応が必要
  • インターネットバンキングの不正送金対策
  • 電子契約等でのデジタル署名・証跡の保全
MAC
(Message Authentication
Code : メッセージ認証符号)
 共通鍵を用いてメッセージの 完全性 と
送信元認証を実現する符号の総称
実現方式によりHMAC(ハッシュ関数を利用)、
CMAC(ブロック暗号を利用)等に分かれる
デジタル署名と異なり共通鍵方式のため、
第三者への証明(否認防止)はできない
sequenceDiagram participant A as 送信者 participant B as 受信者 A->>A: 1. 共通鍵とメッセージからMAC値を計算 A->>B: 2. MAC値をメッセージに付与して送信 B->>B: 3. 同じ共通鍵でMAC値を再計算 B->>B: 4. 一致すれば改ざんなし・正当な送信元と確認
手順内容
1送信者が共通鍵とメッセージからMAC値を計算する
2MAC値をメッセージに付与して送信する
3受信者が同じ共通鍵でMAC値を再計算する
4一致すれば改ざんなし・正当な送信元と確認する
  • 完全性と送信元認証を実現できる
  • デジタル署名より高速・軽量
  • 共通鍵の事前共有・安全な管理が必要(鍵配送問題)
  • 送信者・受信者のどちらも作成できるため否認防止はできない
  • メッセージの完全性検証
  • 送信元認証(なりすまし対策)
HMAC
(Hash-based Message
Authentication Code)
 MACの実現方式の一つ
共通鍵とハッシュ関数を
組み合わせて実装するメッセージ認証符号
HMAC = H(鍵 XOR opad || H(鍵 XOR ipad || メッセージ))
ハッシュ関数単体(メッセージダイジェスト)と異なり
鍵を知らないと正しいMAC値を計算できない
sequenceDiagram participant A as 送信者 participant B as 受信者 A->>A: 1. SHA-256等のハッシュ関数を選択 A->>A: 2. 共通鍵とメッセージからHMAC値を計算 A->>B: 3. HMAC-SHA256のように組み合わせて利用(メッセージとHMAC値を送信)
手順内容
1SHA-256等の任意のハッシュ関数を選択する
2共通鍵とメッセージから上記の式でHMAC値を計算する
3HMAC-SHA256のように組み合わせて利用する
  • 任意のハッシュ関数と組み合わせられ、高速で広く実装されている
  • 単純なH(鍵 || メッセージ)より安全な構成(長さ拡張攻撃への耐性)
  • 共通鍵の管理が必要で、否認防止はできない

5IdPは、SPのACS(Assertion Consumer Service)URLを宛先とする自動送信フォーム(method=POST)のHTMLをブラウザに返す
hiddenフィールドにSAMLResponse(XMLをBase64エンコードしたもの、圧縮なし)とRelayStateを持ち、ブラウザがこれをSPへPOSTする(HTTP-POSTバインディング)
6SPのACSがバインディングに応じてSAML Responseを取り出す
  • HTTP-POST(一般的) : POSTリクエストのボディ(application/x-www-form-urlencoded)のSAMLResponseパラメータ → Base64デコード
  • HTTP-Redirect : GETのクエリ文字列のSAMLResponseパラメータ → URLデコード → Base64デコード → DEFLATE展開(署名はXML内ではなくSigAlg・Signatureパラメータ)
  • HTTP-Artifact : クエリ/ボディのSAMLartをIdPへバックチャネルで送り、Responseを取得
XMLをパースする(XXE対策としてDTD・外部エンティティは無効化)
7SPが署名とアサーションの内容を検証する(詳細は下記の検証項目表)
  1. 署名 : POST/ArtifactはXML署名、Redirectはクエリ文字列に対するSignatureを、事前登録したIdPの証明書で検証する(利用するAssertionが署名で保護されていること)
  2. Response : Status、Issuer、Destination、InResponseTo
  3. Assertion : Issuer、Subject/SubjectConfirmation(bearer・Recipient・NotOnOrAfter・InResponseTo)、Conditions(有効期間・Audience)、AuthnStatement(認証時刻・認証方法)、属性
  4. AssertionのIDのリプレイ検査
8検証に成功したら、NameID・属性からSP側のユーザに対応付けてSPのセッションを確立(Set-Cookie)し、RelayStateで元のURLへ遷移させる(RelayStateは遷移先を検証すること)

チケット型SSO
(Kerberos認証)
  • 共通鍵暗号とチケットに基づくネットワーク認証プロトコル(RFC 4120)
  • パスワード(由来の鍵)をネットワークに流さずに、クライアントとサービスが相互認証できる
  • 登場人物 : KDC(鍵配布センタ、AS=認証サービス + TGS=チケット発行サービス、ADではドメインコントローラ)、クライアント、サービスサーバ
  • TGT(Ticket Granting Ticket)は、KDCの鍵(krbtgtアカウント)で暗号化された「ログイン済み」の証明で、サービス用チケットの発行要求に使う(クライアントは中身を読めない)
  • ST(Service Ticket、TGS/サービスチケット)は、サービスの鍵で暗号化された、特定サービスへのアクセス用チケット
  • 認証子(Authenticator)は、クライアント名と時刻をセッションキーで暗号化したもの
  • チケットの使い回し(リプレイ)を防ぐ
  • 時刻同期が必須(既定では±5分以内)
  • メッセージ・鍵の詳細は「認証手順」欄、TGT/ST・鍵を狙う攻撃は「デメリット」欄の表を参照

手順内容
1【AS交換】クライアントがKDC(AS)にAS-REQを送る(ユーザ名・要求先krbtgt、事前認証として、現在時刻をユーザの鍵(パスワード由来)で暗号化したタイムスタンプを付与)
2KDCは事前認証を検証し、AS-REPを返す
内容は(a)TGT(krbtgtの鍵で暗号化)と(b)TGS用セッションキー(ユーザの鍵で暗号化)
クライアントはパスワードから導出した鍵で(b)を復号する
3【TGS交換】サービス利用のたびに、クライアントがTGS-REQを送る(TGT + 認証子(TGSセッションキーで暗号化) + 接続先サービスのSPN)
4KDC(TGS)はTGTをkrbtgtの鍵で復号して認証子を検証し、TGS-REPを返す
内容は(a)ST(サービスの鍵で暗号化、ADではグループ情報等のPACを含む)と(b)サービス用セッションキー(TGSセッションキーで暗号化)
5【AP交換】クライアントがAP-REQとして、ST + 認証子(サービスセッションキーで暗号化)をサービスへ送る
6サービスは自身の鍵でSTを復号してセッションキー・クライアント名・有効期限等を取り出し、認証子を復号して時刻・リプレイを検証する(KDCへの問い合わせは不要)
7相互認証の場合、サービスがAP-REP(認証子の時刻をセッションキーで暗号化)を返し、クライアントがサービスの正当性を確認する
以降はセッションキーで通信を保護できる

PAM
(Privileged Access
Management : 特権アクセス管理)
 管理者権限等の特権アカウントの利用を
制御・監視・記録する仕組み
  • 特権IDの貸出・払い出しとパスワードの管理(必要なときだけ利用させる)
  • 承認ワークフローによる利用許可

sequenceDiagram participant U as 利用者 participant W as 承認者 participant P as PAM基盤 participant T as 対象システム U->>P: 1. 特権IDの利用を申請 P->>W: 2. 承認ワークフローで承認を依頼 W-->>P: 2. 利用を許可 P-->>U: 3. 必要な期間だけ特権IDを貸出・払い出し U->>T: 4. 特権IDで操作 P->>P: 4. 利用中の操作ログ・画面操作を記録
手順内容
1利用者が特権IDの利用を申請する
2承認ワークフローで承認者が利用を許可する
3必要な期間だけ特権IDを貸出・払い出す
4利用中の操作ログ・画面操作を記録する
  • 特権IDの不正利用・乗っ取りを抑止できる
  • 操作の証跡により内部不正を抑止できる
  • 必要な期間・用途に限定して貸し出せる
  • 承認ワークフローにより運用負荷がかかり、緊急時の対応設計が必要
  • PAM基盤自体が侵害されると影響が極めて大きい
  • 導入コスト
  • 管理者権限(特権アカウント)の不正利用・乗っ取り対策
  • 内部不正の抑止と証跡の取得
