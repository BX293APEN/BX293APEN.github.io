# セキュリティサービス

## ネットワーク防御

| サービスの種類 | 説明 | 製品例 |
| --- | --- | --- |
| <strong>ファイアウォール</strong> | <ul><li>基本的な防御機構</li><li>ネットワークの境界でパケットの送受信を制御する</li><li>不正な通信を遮断する</li><li>あらかじめ定めたルール(許可/拒否)に基づいて通信を制御する</li><li>ルールの考え方(FW・IPS共通)(「共通の考え方・基盤技術」を参照)<ul><li><strong>ブラックリスト方式</strong>：不正なIPアドレスの遮断、脅威インテリジェンスの悪性IPリストの活用</li><li><strong>ホワイトリスト方式</strong>：許可する通信(IPアドレス・ポート)のみ開放し、それ以外を拒否する</li></ul></li></ul> | - |
| └ パケットフィルタリング型 | <ul><li>最も基本的な方式</li><li>送信元/宛先IPアドレス、ポート番号、プロトコル等のパケットのヘッダ情報のみでルールベースの許可・拒否を判定する</li><li>OSI参照モデルの第3層(ネットワーク層)・第4層(トランスポート層)で動作する</li><li>高速</li><li>パケットの中身(ペイロード)は検査しない</li><li>通信ごとの状態は見ない</li><li>戻りパケット用のルールをあらかじめ固定的に開けておく必要がある</li></ul> | - |
| └ ダイナミックパケットフィルタリング型 | <ul><li><strong>ステートフルパケットフィルタリング型とほぼ同一</strong>(呼称の違い)</li><li>通信の往路(要求)を監視する</li><li>通信状況に応じてフィルタリングルールを自動生成する<ul><li>戻りパケットのみを動的に許可する等</li></ul></li><li>通信が終了したらそのルールを削除する</li><li>ポートを開けたままにするリスクを減らせる</li></ul> | - |
| └ ステートフルパケットフィルタリング型（ステートフルインスペクションFW） | <ul><li><strong>ダイナミックパケットフィルタリング型とほぼ同一</strong>(呼称の違い)</li><li>セッション(コネクション)の状態を管理・追跡する</li><li>同一セッションに属する通信のみを許可する</li><li>なりすましや不正な戻りパケットを排除する</li><li>通信の開始から終了までの状態をテーブルで管理する</li><li>TCPの接続手順等に沿わない通信を遮断する</li></ul> | - |
| └ アプリケーションゲートウェイ型（プロキシ型FW） | <ul><li>アプリケーション層(OSI第7層)の内容まで解析する</li><li>通信を代理(プロキシ)する</li><li>内部と外部の通信を直接つながない</li><li>クライアント側とサーバ側で別々のセッションを張って中継する</li><li>厳密な制御ができる</li><li>処理負荷が高い</li><li>プロトコルごとに対応するプロキシが必要</li><li>検査精度が高い</li><li>プロキシの考え方は「Web・メール防御」のプロキシサーバを参照</li></ul> | - |
| <strong>UTM</strong>（統合脅威管理） | <ul><li>ファイアウォール、IDS/IPS、アンチウイルス、アンチスパム、URLフィルタリング等の複数のセキュリティ機能を1台に統合した製品</li><li>ネットワークの出入口(ゲートウェイ)に設置する</li><li>一括で防御する</li><li>メリットとデメリット<table><thead><tr><th>区分</th><th>内容</th></tr></thead><tbody><tr><td>メリット</td><td><ul><li>運用・管理の一元化ができる</li><li>コスト削減ができる</li></ul></td></tr><tr><td>デメリット</td><td><ul><li>1台に集中するため障害時の影響が大きい<ul><li><strong>単一障害点</strong></li></ul></li><li>全機能を有効にすると処理性能が低下しやすい</li></ul></td></tr></tbody></table></li></ul> | - |
| <strong>IDS（不正侵入検知システム）/ IPS（不正侵入防止システム）</strong> | <ul><li>IDS<ul><li>ネットワークやホスト上の不正な兆候を検知する</li><li>管理者に通知する</li></ul></li><li>IPSは検知に加えて、不正な通信をリアルタイムに遮断する</li></ul> | - |
| └ IDS | <ul><li>ネットワークやホスト上の不正な兆候を検知する</li><li>管理者に通知する</li><li>通信の遮断はしない</li><li>監視対象により、ネットワーク型の「NIDS」とホスト型の「HIDS」(「エンドポイント防御」を参照)に分けられる</li><li>検知方式<table><thead><tr><th>方式</th><th>判定の基準</th><th>長所</th><th>短所</th></tr></thead><tbody><tr><td>シグネチャ型(ミスユース検知)</td><td><ul><li>既知の攻撃パターンと照合する</li><li>一致したものを不正と判定する(ブラックリスト的)</li></ul></td><td>既知の攻撃には確実</td><td>未知の攻撃には対応できない</td></tr><tr><td>アノマリ型(異常検知)</td><td><ul><li>正常時の状態を基準とする</li><li>そこから逸脱したものを不正と判定する(ホワイトリスト的)</li></ul></td><td>未知の攻撃にも対応できる可能性がある</td><td>誤検知が起こりやすい</td></tr></tbody></table></li></ul> | Snort |
| └ NIDS（ネットワーク型IDS） | <ul><li>ネットワーク上を流れるパケットを監視する</li><li>ネットワークセグメント全体に対する不正アクセスの兆候を検知する</li><li>1台のセンサで複数のホストを監視できる</li><li><strong>暗号化された通信(HTTPS等)の中身は検査できない</strong></li></ul> | - |
| └ IPS | <ul><li>IDSの機能に加えて、検知した不正な通信をリアルタイムに遮断する機能を持つ</li><li>設置方法(動作モード)によって遮断できるかどうかが変わる(下記の2つ)</li><li>検知方式<table><thead><tr><th>方式</th><th>判定の基準</th><th>長所</th><th>短所</th></tr></thead><tbody><tr><td>シグネチャ型(ミスユース検知)</td><td><ul><li>既知の攻撃パターンと照合する</li><li>一致したものを不正と判定する(ブラックリスト的)</li></ul></td><td>既知の攻撃には確実</td><td>未知の攻撃には対応できない</td></tr><tr><td>アノマリ型(異常検知)</td><td><ul><li>正常時の状態を基準とする</li><li>そこから逸脱したものを不正と判定する(ホワイトリスト的)</li></ul></td><td>未知の攻撃にも対応できる可能性がある</td><td>誤検知が起こりやすい</td></tr></tbody></table></li><li>アノマリ型は誤検知が起こりやすいため、基準の調整・学習段階は通信が止まらないプロミスキャスモード(通知のみ)で運用するのに向く</li></ul> | Snort |
| └ IPSインラインモード | <ul><li>通信経路上に直接設置する</li><li>通過するすべての通信を検査した上で転送する</li><li>不正な通信をリアルタイムに遮断できる</li><li>通信経路上にあるため、IPS自体の障害・性能不足が通信全体に影響する(<strong>単一障害点</strong>)</li><li><strong>誤検知した場合の影響</strong>：正常な通信まで遮断される。業務への影響が大きい</li></ul> | - |
| └ IPSプロミスキャスモード（パッシブモード） | <ul><li>スイッチのミラーポート(SPAN)やタップ等から通信のコピーを受け取って監視する</li><li>通信経路上には存在しない</li><li>不正な通信そのものを遮断することはできない</li><li>検知(IDS的な用途)にとどまる</li><li>TCPリセットの送信等で接続の切断を試みる製品もある</li><li>確実な遮断とはいえない</li><li><strong>誤検知した場合の影響</strong>：通知が増えるだけで通信は止まらない(IDSも同様)</li></ul> | - |
| <strong>NDR</strong>（Network Detection and Response） | <ul><li>ネットワークトラフィックを分析する</li><li>異常な通信パターンや侵害の兆候を検知する</li><li>対応を支援する仕組み</li><li>次の用途に有効<ul><li>EDRを導入できない機器(IoT・OT機器、未管理の端末等)の監視</li><li>侵入後の内部での横展開(ラテラルムーブメント)の検知</li></ul></li></ul> | - |
| <strong>検疫ネットワーク</strong>（検疫ネットワークシステム） | <ul><li>社内ネットワークへの接続前に、端末のセキュリティ状態(パターンファイルの更新状況、パッチ適用状況等)を検査する専用の隔離ネットワーク</li><li>基準を満たさない端末は本番ネットワークへの接続を許可しない<ol><li>端末が接続しようとするとまず検疫用の隔離ネットワークに接続させる</li><li>OSのパッチやウイルス対策ソフトのパターンファイル等の状態を検査する</li><li>基準を満たさない端末は隔離環境で修復(パッチ適用・パターンファイル更新等)する</li><li>基準を満たしたことを確認してから本番ネットワークへの接続を許可する</li></ol></li></ul> | - |
| <strong>ZTNA</strong>（ゼロトラストネットワークアクセス） | <ul><li>「何も信頼しない」ことを前提とする</li><li>通信のたびにアクセス主体(ユーザ・デバイス)を検証・認可する仕組み</li><li>従来のVPNとの違い<table><thead><tr><th>方式</th><th>接続範囲</th></tr></thead><tbody><tr><td>従来のVPN</td><td>接続後に社内ネットワーク全体へアクセスできてしまいがち</td></tr><tr><td>ZTNA</td><td>許可されたアプリケーションにのみ接続させる</td></tr></tbody></table></li><li><strong>SPA</strong>(Single Packet Authorization)<ul><li>ポートノッキングの発展形</li><li>認証情報を含む暗号化・署名済みの<strong>1パケット</strong>で認可を行う</li><li>ZTNAのSDP(Software Defined Perimeter)等で接続制御に使われる</li></ul></li><li>ポートノッキングとSPAの違い<table><thead><tr><th>項目</th><th>ポートノッキング</th><th>SPA</th></tr></thead><tbody><tr><td>認証の仕組み</td><td>決められたポートへ決められた順序で接続を試みる</td><td>暗号化・署名された認可パケットを1つ送る</td></tr><tr><td>認証情報</td><td>ポートの順序(合言葉のようなもの)</td><td>暗号化・署名されたペイロード</td></tr><tr><td>盗聴・リプレイ攻撃</td><td>順序を盗み見られると再利用される</td><td>タイムスタンプやナンス等で再利用を防げる</td></tr><tr><td>なりすまし・改ざん</td><td>順序を再現されると防げない</td><td>HMAC等の署名で検出できる</td></tr><tr><td>実装例</td><td>knockd</td><td>fwknop</td></tr></tbody></table></li><li>SPAの流れ<ol><li>サーバは全ポートを閉じ、応答を返さない(外部からは存在しないように見える)</li><li>クライアントが認可パケットを1つ送る</li><li>サーバは<strong>ポートを開けずに</strong>パケットを受け取り検証する</li><li>検証に成功した送信元IPに限り、指定ポートを一時的に開放する</li><li>一定時間後にルールを自動で削除する</li></ol></li></ul> | - |
| <strong>DDoS対策</strong> | <ul><li>大量の通信によるサービス停止攻撃に対する耐性を高める</li></ul> | - |
| └ DDoS対策サービス（スクラビングサービス） | <ul><li>大量トラフィックを専用設備(スクラビングセンタ)で吸収・選別する</li><li>正常な通信のみをオリジンサーバへ転送する</li><li>DNSの切り替えやBGP経路の広告により、通信をスクラビングセンタへ迂回させる</li></ul> | - |
| └ CDN（コンテンツデリバリネットワーク） | <ul><li>コンテンツを世界各地のエッジサーバに分散配置(キャッシュ)する</li><li>利用者に近いサーバから配信する</li><li>負荷分散やDDoS攻撃に対する耐性を高められる</li><li><strong>エッジサーバがリバースプロキシとして応答する</strong></li><li>オリジンサーバを直接公開せずに済む</li></ul> | - |
| <strong>DNSSEC</strong> | <ul><li>DNS応答に電子署名を付与する</li><li>DNSキャッシュポイズニング等の改ざんを検知可能にする仕組み</li><li>権威DNSサーバが署名する</li><li>キャッシュDNSサーバ(フルサービスリゾルバ)が検証する</li><li>応答の真正性・完全性を確認できる</li><li>通信内容の暗号化(秘匿)は行わない</li></ul> | - |
