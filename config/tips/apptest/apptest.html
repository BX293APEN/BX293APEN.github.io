実験計画法
  • 直交表テスト
  • 組合せテスト
  • ペアワイズ法 (All-pairs) は関連技法
 ブラックボックス 因子と水準を直交表に割り付け、少ない組合せで各因子の影響を評価する
  1. 因子と水準を洗い出す
  2. 因子・水準数に合う直交表 (L4, L8, L9 等) を選ぶ
  3. 因子を直交表の列に割り付ける
  4. 各行をテストケースとして実行する
  5. 要因効果図・分散分析で結果を分析する
  • 組合せ爆発を抑えられる
  • 各因子の影響を偏りなく評価できる
  • 例: 3因子2水準の全組合せ 8 件を L4 直交表で 4 件に削減
  • 直交表や統計の知識が必要
  • 3因子以上の交互作用は検出しにくい
  • 禁止組合せ等の制約を扱いにくい
  • OS・ブラウザ・設定値の組合せ検証
  • パラメータ調整
  • 構成テスト
状態遷移テスト
  • 状態遷移図・状態遷移表テスト
  • N スイッチカバレッジ
 ブラックボックス 状態・イベント・遷移でシステムをモデル化し、遷移の正しさを確認する
  1. 状態・イベント・アクションを抽出する
  2. 状態遷移図または状態遷移表を作成する
  3. カバレッジ基準を決める
    • 全状態
    • 全遷移 (0 スイッチ)
    • 連続 N 遷移 (N スイッチ)
    • 無効遷移 (状態とイベントの不正な組合せ)
  4. テストケースを導出して実行する
  • 状態に依存する振る舞いを体系的に確認できる
  • 仕様の抜け・矛盾を発見できる
  • 無効遷移のテストも設計できる
  • 状態数が多いと図・表が複雑になる
  • 状態を持たない処理には不向き
  • N スイッチの N を増やすとテスト数が急増する
  • 組込み機器の制御
  • 画面遷移
  • 注文・申請のステータス管理
  • 通信プロトコル
探索的テスト
  • ET
  • セッションベーステスト (SBT)
  • 経験ベーステスト
 経験ベース テストの学習・設計・実行を同時に進め、得られた知見を次のテストに反映する
  1. チャータ (テストの目的・対象範囲) を作成する
  2. 時間枠 (60〜120 分程度) を決める
  3. 探索しながらテストを設計・実行する
  4. 気付き・不具合・疑問を記録する
  5. デブリーフィング (振り返り) で共有する
  • 事前準備が少なく素早く開始できる
  • 想定外の不具合を発見しやすい
  • 仕様が不十分でも実施できる
  • テスターの経験・スキルに依存する
  • 網羅性を保証できない
  • 再現性・品質の説明が難しい
  • 仕様書が乏しい開発
  • アジャイル開発
  • リリース前の最終確認
  • 他の技法を補完するテスト
モデルベースドテスト
  • MBT
 モデルベース テスト対象の振る舞いをモデル化し、モデルからテストケースを自動生成する
  1. 仕様からモデルを作成する
    • 状態機械
    • UML
    • マルコフ連鎖 等
  2. モデルを検証する
  3. カバレッジ基準を指定してテストケースを自動生成する
  4. テストスクリプトに変換して実行する
  5. 期待結果をモデルと比較する
  • テストケースの網羅性を機械的に確保できる
  • 仕様変更時はモデル修正だけで再生成できる
  • モデル作成が仕様レビューを兼ねる
  • モデル作成の初期コストが大きい
  • モデリングスキルとツールが必要
  • モデルの誤りがテストに伝播する
  • 大規模・複雑なシステム
  • 自動車・鉄道等の安全性が重要な分野
  • 長期保守する製品の回帰テスト
同値分割
  • 同値クラステスト
 ブラックボックス 入力を同じ振る舞いをする集合 (クラス) に分け、各クラスから代表値を選ぶ
  1. 入力条件を洗い出す
  2. 有効クラスと無効クラスに分割する
  3. 各クラスから代表値を 1 つ選ぶ
  • テスト数を大幅に削減できる
  • 無効入力の確認も体系化できる
  • クラス境界付近の不具合を見逃す
  • 分割の妥当性は仕様理解に依存する
  • 入力値の範囲チェック
  • 入力フォームの検証
境界値分析
  • BVA
 ブラックボックス 同値クラスの境界とその前後の値でテストする
  1. 同値分割でクラスを決める
  2. 各クラスの境界値を特定する
  3. 境界値とその前後の値を選ぶ
    • 例: 範囲 1〜100 なら 0, 1, 100, 101
  • 境界の比較演算子の誤り (< と ≤ 等) を検出できる
  • 少ないテスト数で不具合を検出しやすい
  • 境界のない入力には使えない
  • 複数入力の組合せは扱えない
  • 数値・日付・文字数の範囲チェック
  • 配列・バッファの上下限
デシジョンテーブルテスト
  • 決定表テスト
  • 原因結果グラフ (関連技法)
 ブラックボックス 条件の組合せとそれに対する動作を表にして、各組合せをテストする
  1. 条件と動作を抽出する
  2. 条件の組合せを列挙して表を作る
  3. 不可能な組合せを除外し、同じ動作の列をまとめる
  4. 各列 (ルール) を 1 テストケースにする
  • 条件の組合せの漏れ・矛盾を発見できる
  • 複雑なビジネスルールを整理できる
  • 条件数が多いと表が巨大になる
  • 条件が独立でない場合は整理が必要
  • 料金計算・割引判定
  • 審査・承認ルール
エラー推測
  • エラーギャッシング
  • 経験則テスト
 経験ベース 過去の不具合や経験から、不具合が起きやすい箇所を推測してテストする
  1. 過去の不具合・よくある誤りを調べる
  2. 不具合の起きやすい入力・操作を列挙する
  3. リストに基づきテストを実行する
  • 他の技法で見逃す不具合を検出できる
  • 低コストで実施できる
  • 属人的で網羅性がない
  • 経験がないと効果が出にくい
  • 他の技法の補完
  • よくある不具合 (NULL、0、空文字、特殊文字等) の確認

インスペクション

  • 責任と手順が明確
  • 工数がかかる
  • 手順が厳格で小規模開発には重い
  • 参加者のスキルと準備に依存する
  • 安全性が重要なシステムの仕様・設計
  • 品質ゲートとなる成果物の承認

ビッグバンテスト
  • 一括結合テスト

  • すべてのモジュールを一度に結合する

  1. 全モジュールの単体テスト完了を確認する
  2. 全モジュールを一括で結合する
  3. システム全体をテストする
  4. 不具合の原因を切り分ける
  • スタブ・ドライバが不要

  • 原因の特定が困難

トップダウンテスト
  • トップダウン結合テスト
 結合方式
  • 最上位モジュールから下位へ順に結合する
  • 未完成の下位モジュールはスタブで代替する
  1. 最上位モジュールをテストする (下位はスタブ)
  2. 下位モジュールを実物に順次置き換える
  3. 置き換えるたびにテストする
  • 上位の制御構造や主要フローを早期に検証できる
  • ドライバが不要
  • 早期に動作するデモを作れる
  • スタブを多数作る必要がある
  • 下位の入出力・低レベル機能の検証が遅れる
  • スタブが複雑化しやすい
  • 画面・業務フロー中心のシステム
  • 上位設計が先に固まる開発
ボトムアップテスト
  • ボトムアップ結合テスト
 結合方式

  • 未完成の上位モジュールの代わりにドライバを使う
  1. 最下位モジュールをドライバでテストする
  2. 上位モジュールと結合してテストする
  3. 最上位まで繰り返す
  • スタブが不要
  • 下位の基盤機能を早期に確認できる
  • テスト環境を用意しやすい
  • 上位の制御や全体動作の確認が最後になる
  • ドライバの作成が必要
  • 設計上の欠陥の発見が遅れる
  • ライブラリ・基盤層
  • 下位モジュールが先に完成する開発
サンドイッチテスト
  • ハイブリッド結合テスト
  • 混合結合テスト
 結合方式
  • 上位層はトップダウンで結合する

  2. 上位層をトップダウンでテストする (スタブ使用)
  3. 下位層をボトムアップでテストする (ドライバ使用)
  4. 中間層で両者を結合してテストする
  • 並行して進められ、工期を短縮できる
  • 上位・下位の双方を早期に検証できる
  • 計画と管理が複雑
  • スタブとドライバの両方が必要
  • 中間層の扱いが難しい
  • 大規模で階層が深いシステム
  • チーム分担での開発
